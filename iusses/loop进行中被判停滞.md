## 问题与影响

【建议】2026-10-27 约 03:15（UTC），飞书推来「personal agent-dev分支 的 loop 干到一半没动静了」。实际上 loop 在正常工作：误报修复批第 1 轮评审在 22:52（纽约时间）结束，判了需返修；Pi 返修到 23:06，第 2 轮评审 23:08 还在写会话记录。卡片正文「最后在做」写的是验收标准最后一条「A10. [人工] 操作：…」，看不出 loop 在干什么。

不修的后果：每批 loop 只要一轮（开发加评审加验收）超过 30 分钟，就会误报一次。真机修复批一轮就用过 50 分钟。

## 因果链

```
loop 总结只在每轮结束时更新
→ 盯防按「总结 30 分钟没有新记录」判停滞
→ 一轮超过 30 分钟就误报
→ 「最后在做」取的是总结文件的最后几行，正好是验收标准，不是进度
```

（来源：协调方核对 loop 总结和 Pi 会话记录的修改时间，推断。）

## 分层归因

- 产品实现：loop 的「停滞」只看总结文件，没看开发会话和评审会话是否还在写记录；「最后在做」取错了内容。
- 需求：停滞规则（30 分钟没动静）是按单个 AI 会话定的，没考虑 loop 一轮天然就很长。

## 处理方向

1. loop 的停滞改看它的开发、评审、验收会话里最近一次的记录时间；都没动静才算停滞。
2. 「最后在做」写 loop 当前在哪一步（开发 / 评审第几轮 / 验收），不要取总结末尾的文字。
