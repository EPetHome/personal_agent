# 飞书连接状态写入失败，卡死收件和检测

状态：已修复、待你核销（2026-10-27 合入 `f4089a6` 并升级真机，修复见[提示词-飞书体验](../docs/prompt/xx/提示词-飞书体验.md)；热修那一行已被本批代码取代并经 loop 评审，连接状态显示也一并修了）。在真实飞书里确认后移进 `【已完成】/`。

## 问题与影响

【必须修改】误报修复批合入、真机服务重启后，每轮检测都失败（03:24 起，日志「检测未完成，保留事实与现场；下轮重试」），收件每秒报一次「收件暂未完成，下次重试」。盯防实际停摆了约 10 分钟，期间不会叫用户。

## 因果链

```
服务启动 → 飞书开始连接，程序要把「连接状态」写进数据目录（要拿数据锁，最多等 30 秒）
        → 同时第一轮检测启动，拿着数据锁跑了约 2 分钟
        → 写「已连上」等锁超时，这次写入失败（code/src/channels/feishu/index.ts 的 reportConnection）
        → 失败的写入一直留在 connectionWrites 里；连接状态不再变化，就没有新的写入替换它
        → 每次处理收件（drain）都先 await connectionWrites → 每次都报错
        → 检测每轮结束都要处理飞书收件 → 整轮检测失败
```

（来源：协调方读源码，并在数据副本上验证：数据本身没问题，单独处理收件能成功。）

## 分层归因

- 产品实现：「连接状态」只是用来展示的，却挡在收件和检测前面；写入失败后没有重试，也不放行。
- 验证：自动验收用的是飞书替身，没有出现「检测长时间占着锁」与「连接状态变化」同时发生的情况；评审没有指出锁的顺序问题。
- 流程：用户让停掉自动验收、直接合入。这次即使验收跑完也测不出来，但合入后协调方只盯了「换上新代码」，没有马上核对第一轮检测是否成功。

## 已做（热修）

- `drain` 里改成 `await connectionWrites.catch(() => {})`：连接状态写不进去，也不影响收件和检测。门禁 289 项通过。
