# 升级后，几周前就暂停的 loop 一次推了 44 张「停下了，需要你决定」

状态：收集中（2026-10-28 23:54 真机发现，提醒都发飞书批引入），一次性爆发，已去重不会再发；等同源归并排批。

## 问题与影响

「提醒都发飞书」上真机后约 10 分钟（23:54），飞书一次收到 44 张 loop 暂停卡片，全是「XX 的 loop（批次名暂未记录）停下了，需要你决定」，卡片时间都写「今晚 23:45」。这些 loop 实际是 10-05 到 10-25 暂停的旧批次，用户早不关心，以前也从没提醒过。影响：一次刷屏，真正要处理的卡片被淹掉；卡片时间写成今晚，误导用户以为刚发生。

## 事实

- 真机 `feishu-sent.jsonl`：23:44 之后发 48 张，其中 23:54 一分钟 44 张，全是 `loop_paused`；`outbox.jsonl` 里这 44 条的 `evidenceAt` 都是 `2026-10-29T03:45:19Z`（升级后第一轮检测）。
- 这 44 条的会话以前没有任何 `loop_paused` 提醒；对应总结文件修改日期 10-05 至 10-25（协调方只读核实）。
- 提示词已拍板第 2 条：loop 暂停「取不到暂停时间，就从第一次看到暂停算」。旧 loop 总结没有暂停时间，升级后第一轮把「第一次看到」记成当下，5 分钟后全部当新暂停发出。
- 自动验收 A8 只验了「已经发过的旧提醒不补发」，没覆盖「从没提醒过的旧暂停」。

## 因果链

```
升级后第一轮检测 → 旧暂停 loop 没有暂停时间 → 记「第一次看到 = 23:45」
  → 绕过了原来「太旧的只进总览、不提醒」的判断
  → 5 分钟后仍是暂停 → 44 张一起发出
```

## 分层归因

属「提醒都发飞书」的 loop 暂停等候计时。上游是 loop 来源取不到暂停时间（`code/src/sources/loop/index.ts`），下游是首次接入「太旧只进总览」的规则。同根还有评审留下的建议：暂停后恢复再暂停，计时可能沿用旧起点。

## 处理方向

取不到暂停时间时，用总结文件的时间或最后活动时间作暂停时间，太旧的照旧只进总览；新出现的 loop 来源目录同样适用。补一条「升级时有几周前暂停、从没提醒过的 loop」的回归。
