# 评测集准备（personal agent）：从已有记录里收第一批状态判定题

## 目标

personal agent 的终极目标是：替用户盯住所有 AI，**该叫时叫，不该叫不叫，叫了看得懂**。现在每次改判断规则、提示词或模型，好坏只能凭感觉判断，也说不出误报率和漏报情况。

运行记录其实已经很全：`~/.personal-agent/data/` 里有 `events.jsonl`（观察、模型判断、计划推送、抑制、送达）、`outbox.jsonl`（每张卡片和快照）、`feedback.jsonl`（飞书按钮：正确、误报、漏了、看不懂）。本批**只读这些记录，把它们收成第一批评测题**，按与 Loop、产品智能体统一的结构放进仓库 `eval/`。

第一批只评**状态判定**：在等你、疑似跑偏、停滞、loop 暂停、loop 完成判得对不对，以及该不该推。卡片写得懂不懂放到下一批，本批只登记。

## 已拍板

- 题放在仓库根的 `eval/`。真实内容（会话片段、卡片原文）只放 `eval/cases/<id>/`、`eval/runs/`、`eval/待标注/`，这三处加进 `.gitignore`，不进任何提交。纳入版本管理的只有 `README.md`、`判定点.md`、检查脚本和 `报告/`，`报告/` 里只写数字和编号，不复述会话内容。
- 本批不回放、不调用模型。回放会占用每日模型额度，单独开一批，并设调用上限。
- 判断标准以需求书为准：`docs/requirements/需求书-personal-agent.md`「什么时候叫我」一段，以及第 30、91 行对跑偏的定义。

### 统一结构（两个项目逐字一致，不得改字段名和层级）

```
<评测根>/                      本项目为 eval/
├─ README.md                   做法、规矩、题目清单；本节结构说明写进这里
├─ 判定点.md                   跨题共用的判定点（本项目：状态判定、推送决策、卡片的判定点和过程断言）
├─ cases/
│   ├─ <id>.yaml               一道题
│   └─ <id>/                   这道题的原件、附件、工具 mock（可选）
├─ runs/<日期>/<id>/
│   ├─ 产物.md                 被测这次的输出；多个文件时放 产物/ 目录
│   ├─ trace.jsonl             这次的轨迹，一行一步
│   └─ 判定.json               逐条判定点的结果和理由
└─ 报告/
    ├─ 成绩单.md               一次运行一行的汇总表
    └─ <日期>.md               需要时写的阶段报告
```

`<id>` 沿用各项目现有编号（本项目新编：J001 起为状态判定题，W001 起为漏报题），不重新编号。`<日期>` 写成 `YYYY-MM-DD`，同一天跑多次时加后缀，如 `2026-10-31-2`。

题目文件 `cases/<id>.yaml`：

```yaml

标题: 平台调研／学习借鉴

层: 能力                         # 能力 / 回归
状态: 草稿                       # 沿用项目自己的状态词
失败类别: []                     # 归类名；还没有就留空
被测对象: 产品智能体

题目:
  原文: cases/Q01/题目.md        # 原话很长或有格式时引用文件；短的可以直接写在这里
  附件: []                       # 相对路径或链接；缺原件时写明

初始环境:                        # 回放时必须能还原的东西
  版本: null
  模型: null
  可回放: false
  不可回放原因: null

    类型: 底线                   # 底线 / 质量 / 成本 / 风格

  - 判定点: S1                   # 本题独有的判定点直接写在这里

    条款: ""
    本题判法: ""
    为什么只属于本题: ""

参考案例:
  - id: C1
    出处: ""
    评价: ""                     # 好 / 坏，加上反馈人原话摘录

过程断言:                        # 可以为空
  必须: []
  绝不: []
  顺序: []
  步数上限: null

关键决策点: []                   # 可以为空；只给权重高的题写

证据: []
扩展: {}                         # 项目自有字段，如 风格项、跑法、模拟用户人设卡
修订:
  - 版本: v1
    日期: 2026-10-30
    内容: ""
```

YAML 只用以下子集，方便两边都用零依赖程序读取：块风格的映射和列表；单行标量（字符串、数字、`true`/`false`、`null`）；多行文本用 `|`；空值写 `[]`、`{}` 或 `null`。不用锚点、引用、流式多行、多文档。

`trace.jsonl` 每行一个 JSON 对象，至少包括：`step`（从 1 开始）、`轮次`、`角色`（用户 / 主理人 / 成员名 / 模拟用户 / 程序）、`动作`（发言 / 工具调用 / 派发 / 交接 / 等待）、`工具`、`摘要`、`开始`、`结束`、`token`、`来源`（原始记录的文件路径和行号）。拿不到的字段写 `null`，不估算。

`判定.json` 至少包括：`caseId`、运行日期、版本、模型、打分方式（人 / 评委，是否盲打）、指标版本，以及 `结果`。`结果` 是一个列表，每项包括 `判定点`、`结论`（有 / 没有 / 不适用 / 数值）、`理由`。

### 初始环境怎么冻住

原会话 7 天后会被封存，所以建题时就把当时的环境存进 `cases/<id>/`：

- 判断时用到的那段会话：从原会话文件里截取到 `evidenceAt` 为止的部分，记下原路径、行号范围和 sha256。原文件已经封存或找不到的，`可回放: false`，并写明原因。
- 对应的 `session_observed` 记录、`model_checked` 记录、卡片（`outbox` 那一行，含 `snapshot`）。
- 当时在跑的代码版本：能从 `service-runs.jsonl`、launchd 记录或基线的「实际运行」推出来的就填，推不出来写 `null`，不要猜。
- 模型名、提示词版本：现有记录里没有的写 `null`，并记进 `报告/` 的「埋点缺口」一节（下一批埋点会补）。

### 漏报：和 loop 记录对账

`loop_paused`、`loop_completed` 有独立的参照来源：

- 从 `~/.pi-autoreview/交付记录.md` 和各项目总结里，列出 personal agent 开始运行以来每一次 loop 暂停和完成（会话 ID、时间）。
- 和 `outbox.jsonl` 里的 `loop_paused` / `loop_completed` 卡片逐条对应，算出召回率。对不上的每一条建一道漏报题（W 编号），同时写明：是被抑制了（查 `notice_suppressed`）、首次接入前不补发，还是没有任何记录。
- `notice_suppressed` 全部列成清单，每条尽量查出是哪条规则抑制的（去重、5 分钟内回话、额度、首次接入）。查不出来的记进「埋点缺口」。

### 判定点.md

先收以下判定点，每条注明需求书或问题单的出处：

- 结果：状态判对（期望类型 vs 实际类型）；该叫没叫（漏报）；不该叫叫了（误报）；卡片看得懂（下一批用）。
- 过程断言（合规，能对着 `events.jsonl` 检查的）：在等你 / 疑似跑偏 / loop 暂停先等 5 分钟；期间用户回了话就不叫；盯防看不见了马上发；【现在就要你】一律发飞书；停滞每个会话只叫一次；首次接入只补最近 1 小时。逐条核对需求书原文；核对不上的标「待定」。
- 汇总指标：误报率（以有标注的卡片为分母）、loop 类召回率、标注覆盖率（有反馈的卡片数 / 卡片总数），每个指标都写清口径。

## 边界

- 只新增 `eval/` 并修改 `.gitignore`。不改 `code/`、`docs/`、`wiki/`、`iusses/`、`AGENTS.md`。
- `~/.personal-agent/`、`~/.pi-autoreview/` 和各工具的会话目录都只读，不停止、不重启服务，不改配置。
- 本任务就是用户授权：可以读取与上面这些题相关的会话片段，并存进 `eval/cases/<id>/`。不读取无关会话；不在报告和对话里复述会话内容；遇到密钥、密码一类内容要跳过，不存。
- 不调用任何模型，不跑回放。不新增 npm 依赖；YAML 按上面的子集自己读写。不提交，不推送。

## 交付物

- 按统一结构建好的 `eval/`：`README.md`、`判定点.md`、`cases/`、`待标注/<日期>.md`、`报告/<日期>.md`。
- `eval/check.ts`（`node eval/check.ts` 可直接运行）：检查每个 `cases/*.yaml` 的必填字段、引用的判定点是否存在、引用的文件是否存在、`cases/<id>/` 里冻住的片段 sha256 是否一致；有错时退出码为 1。
- `报告/<日期>.md`：题目数（按来源、类型、可回放与否分列）、loop 对账的召回率和未对上清单（只列编号）、抑制清单统计、三个汇总指标（带口径）、**埋点缺口**（哪些回放或判定需要的字段现在没有记），以及局限和待补。

## 验收标准

A1. 操作：在项目根执行 `node eval/check.ts`
    预期：全部题目通过，退出码 0；输出题目总数和按来源的分布
A2. 操作：把某个 `cases/<id>/` 里冻住的片段改一个字，再执行 `node eval/check.ts`
    预期：报出该题 sha256 不一致，退出码 1（检查完改回去）
A3. 操作：查看 `eval/cases/`
    预期：18 条飞书反馈都有对应的题或登记；每道题的 `初始环境` 都写明了 `可回放`，`false` 的写了原因
A4. 操作：阅读 `报告/<日期>.md` 的 loop 对账一节
    预期：列出参照来源里暂停和完成的总数、对上的卡片数、召回率，以及每条没对上的编号和原因分类
A5. 操作：阅读 `报告/<日期>.md` 的埋点缺口一节
    预期：每个缺口写明缺什么字段、影响哪类题的回放或判定
A6. 操作：在项目根执行 `git status --short` 和 `git check-ignore eval/cases eval/runs eval/待标注`
    预期：除了开工前已有的改动，只多出 `eval/` 下可以纳入版本管理的文件和 `.gitignore` 的修改；三个目录都被忽略
A7. 操作：在项目根执行 `grep -rn "sk-\|password\|token=" eval/`
    预期：没有命中密钥类内容
A8. [人工] 操作：打开 `eval/待标注/<日期>.md`，按卡片标注
    预期：每张卡片都能看出是哪件事，标得下去
A9. [人工] 操作：对照 Loop 和产品智能体的评测集，看 `cases/<id>.yaml` 和目录
    预期：字段名、层级、命名一致，只有 `初始环境.其他` 和 `扩展` 的内容不同
