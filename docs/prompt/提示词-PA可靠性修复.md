## 边界

### 本批实施范围

**1. 图文输入。** 兼容实际飞书 post 中的文字和图片，把文字组织成用户正文、把图片交给既有附件下载流程。已见消息同时有 `content` 与 `content_v2` 两份同内容结构，不能重复添加同一图片或重复正文；不把图片 key 当作图片内容交给模型。保留独立 image/file、本人过滤、引用/按钮、附件原始名称黑名单与持久化接收行为。

图片类型按实际内容识别和校验，不固定使用 `.png`/`image/png`，也不只凭后缀或上游声明判断。新增接收文件的名称后缀、附件媒体类型和送给模型的 image MIME 应与实际 PNG/JPEG 等支持内容一致；无法识别或不支持时明确说明，不伪装成 PNG。同步处理持久化路径、原始附件名追溯与重启引用，不能因纠正后缀绕过原名黑名单或破坏已有引用。JPEG 对照覆盖图文接收，独立图片接收沿用同一正确类型处理。

可用于构造样例的结构：post 的标题为字符串，content 是二维数组，元素包括 `{tag:"img",image_key:"fixture-image",width:100,height:100}` 和 `{tag:"text",text:"请查看样例图片",style:[]}`；content_v2 可包含同一组内容。所有图片、文字、账号标识均用构造数据，不读取或复制原图、真实文档正文、真实消息 ID。

**2. 真实边界与文件工具。** “我的范围”由程序每轮依据当前已加载、已校验的有效配置及实际工具能力生成，不把目录名单/支持格式手写成提示词中的第二份事实。启动时读取配置、修改后需按规定重启的现有语义保留，不暗中改成每轮热加载权限。将项目、收件箱、附件、当前登记的 Loop 证据运行目录、实际可写子目录、技能和可用工具/格式交给模型，省略凭据和敏感配置。提示词要求以这些事实和实际工具结果为准，没有证据就说明未知，不能猜权限、格式解析结果或执行状态。

增加主助手可用的只读列目录入口，优先复用已有受限文件能力。区分“目录被当文件”“授权范围内路径不存在”“越界”“命中黑名单”和其他读取失败。先核对授权，再检查类型，不能用错误详情泄露越界文件的存在性。

错误原因须贯穿调用链：特别检查 `router.ts` 工具包装层当前统一吞成“工具调用失败或参数不合法”的 catch，以及 `worker.ts` 执行前核对当前统一吞成“核实不了最新状态”的 catch。已知原因以稳定类别和安全说明传给模型及记录；未知异常如实标未知，不编成权限问题。保留兜底和取消处理，不把原始堆栈、凭据、完整请求体或未授权材料直接透传给模型；不能底层已分清、上层又抹掉。

Loop 的能力说明须反映最终生效范围，包括 `loop.ts` 在配置以外追加的禁区（当前含 docs/、wiki/、规则/权限文件等），而非仅展示配置中的 allow/deny。若本批为结果文件修正范围，说明必须同步反映修正后的实际范围。明确 Loop 开发不依赖普通 Pi 的写目录；证据只读当前已登记的授权目录，不把事件里的路径当作新授权。

如实说明两个边界：事件与查询状态核对不上时，当前程序记日志而不主动通知；没有有效事件时，尚无独立发现外部 Loop 进程消失或长期无进展的检测。这里不意味着任何 Loop 失败事件都看不到。本批只修能力说明与错误原因，不新增外部 Loop 失联/停滞检测，也不擅自改变“核实不了不叫用户”的通知策略。

主助手和 Pi 应使用一致的权限事实与格式能力，不另建互相矛盾的白名单。配置建议只使用实际生效字段与校验规则；`pi.readPaths` 不是启动配置的扩权键，派工 readPaths 只会缩小已有范围。对于未知/不生效字段必须明确指出，不能静默接受后宣称已获得权限。

**3. 配置错误的可见性。** 保留主程序的范围校验。业务派工配置不合法时，不能因为看门狗复用整份业务配置校验而让故障报告也一起失效；通知必需字段仍独立校验。有效通知配置下，应能报告业务配置错误；通知配置本身不可用时明确留下本机失败信息，不假称飞书已告警。不得以忽略配置校验、继续使用被撤销的旧权限、输出凭据来解决。只在隔离配置/数据与通知替身中验证，不改真实 launchd 或配置。

**4. 只读文档正文。** 本批明确支持 DOCX 和有文本层的 PDF：对已有读取授权的文档提取正文，保留可理解的段落、表格文字/分页顺序，分段或限量返回。扫描件、受保护文件、损坏文件与超过资源限额的文件必须准确说明未提取/不支持的原因，不把乱码或空结果冒充“已读懂”；本批不包含 OCR、解密、旧 .doc 或编辑 Office 文档。DOCX/PDF 以外未支持的二进制格式（例如真实 XLSX、普通 ZIP）明确返回“不支持该格式”，不能把原始字节按 UTF-8 返回成乱码或冒充正文；不能仅改后缀就被当成已支持格式。保留正常纯文本读取，不将所有非 DOCX/PDF 文件一概拒绝。不写 TXT 产物，不覆盖原件，不开放 Pi 通用命令权限。沿用文件权限、原始附件名检查和资源上限，解析不能绕过拒读或无界解压。

优先复用现有工具和依赖。确需项目内解析依赖时，只在 `code/agent` 的包与锁文件中管理，说明必要性与恢复依据；不安装全局工具、不升级外部 Loop/Pi，不为简单解析另搭框架。

**5. 本次确认。** 改造现有确认与执行记录，落实需求第七节的新规则。模型负责理解任务，程序核对输入来源、本人身份、任务/范围绑定和执行资格；没有可核对的本次明确委托时，仍走原确认流程。补充目标不能扩成未授权动作，未知执行结果不得换编号重发。保留现有派工后更新/发布任务卡及真实状态回报；不要将“已发送请求”冒称“执行完成”。

不重复催办要覆盖“用户没有回复”和“用户选择暂缓”两种情况：没有新事实或本人重新交代时，后续无关问答不追加旧事项催办、不重复索要同一决定。对象/范围明确且没有真实取舍时不凑多选方案。原待办和追溯记录保留，不能靠删除待办、丢弃新输入或全局关闭通知达到“不催”；本人再次问起或真正出现新事实时仍应正常处理。

当前代码已有派工后发布原卡的路径。本批不新定义“已派出”专用卡及新增停止按钮；这些交互尚未拍板。第十二节项目总体验收的措辞由协调方另行对齐，本批按已确认的第七节规则实现，不擅自改旧验收文件。
