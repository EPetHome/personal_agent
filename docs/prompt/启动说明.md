# Pi 启动说明（personal agent）

本项目自己的选择：模型、工具组合、批次开工和合入步骤。loop 怎么用、批次字段和命令输出只看 loop 的 [工具清单](../../../loop/工具清单.md)，这里不重复字段表。版本和路径每次使用前都要核对；最近核对结果只在[基线「当前入口」](../baseline/当前基线与入口.md#当前入口)维护。

## 模型

- 开发：`openai-codex/gpt-6.1-sol`，`max`（`批次.json` 的 `pi`，也是 loop 默认值）。
- 评审：`openai-codex/gpt-6-astra`，`xhigh`（`.autoreview.json` 的 `reviewerModel` / `reviewerThinking`，不写就是这个默认值）。
- 自动验收：`opencode-go/deepseek-v4.1-flash`（`acceptance.model` 的默认值）。
- 写之前用 `pi --offline --list-models <关键字>` 确认型号存在；启动后核对实际加载的模型和档位。

## 工具组合

| 任务 | `批次.json` 的 `tools` | 额外参数 |
|---|---|---|
| 前端、插件、文档、命令行 | `read,edit,write,bash`（默认） | 无 |
| 要跑长构建、起服务 | 再加 `bg_run,bg_status,bg_logs,bg_result,bg_kill` | `args` 里加 `-e pi-background-tasks` |
| 只读调研 | `read,grep,find,ls` | 无 |

权限扩展、loop 和 Ponytail 由 `bin/pi-dev` 固定加载，不用手写。

## 项目固定方法

- 项目配置 `.autoreview.json` 和方法 `.autoreview/methods/` 都在仓库里，每批复用，批次目录不再放 `autoreview.json` 副本或门禁脚本。
- 门禁 `sh .autoreview/methods/gate.sh check`：启用全部已归档的场景样本，再跑 `code/deploy/check.sh`。新批次加了样本目录，在 `gate.sh` 的 `SAMPLES` 和 `self-check.sh` 里各补一行；共享方法确需更新时，在批次边界单独处理，不能把项目根的无关改动一起提交。
- 开发空间：项目根外的 `../personal agent-dev分支/`，各批复用，每批切到自己的分支 `feat/<批次>`（新版 loop 只认 `feat`、`fix`、`refactor`、`docs`、`test`、`chore` 开头）。
- 本机文件：只在本机存在、不进仓库的文件，写进 `.autoreview.json` 的 `localFiles` 并加进忽略规则，`bin/loop 开工` 会把它们复制进开发空间。目前没有这类文件。
- 远端：`origin` = https://github.com/EPetHome/personal_agent ，是公开仓库。**当前不推送**（用户 2026-10-25：先在本地开发），恢复推送要用户授权。
- 项目根停在 `main` 即可，开工、合入都不要求干净；无关的未提交改动保留。开工仍要求开发空间干净；合入时项目根未提交改动与候选涉及同一文件就停止，先处理明确列出的重叠文件。
- 本项目仍由用户启动 Pi、明确说「合入」后才合入；不启用 `merge.auto` / `merge.push`。升级 Loop 不改变既有自动执行模式、工具权限或业务验收授权。

## 开工（每批）

`P` 是项目根，`B` 是批次目录名；开工后使用命令输出中的开发空间批次文件路径。

1. 写提示词 `docs/prompt/提示词-*.md` 和 `docs/batches/$B/批次.json`。一批几段时，每段一份提示词，`steps` 写先后顺序；段的 `scope` 至少禁止改动场景样本（`docs/batches/*/samples`）。
2. 确认本批文件没有密钥、项目根在 `main`、开发空间没有待保留的未提交改动。不再为凑干净而提交全部文档；需要让本批继承的共享需求或方法变更，按项目规则在批次边界单独提交。
3. 核对后开工：

   ```bash
   cd "$P" && /Users/Admin/Desktop/loop/bin/loop 开工 "docs/batches/$B/批次.json" --dry-run
   cd "$P" && /Users/Admin/Desktop/loop/bin/loop 开工 "docs/batches/$B/批次.json"
   ```

   预检沿用已有机制，不是本次新增。实际开工会把本批目录、引用的提示词与验收标准搬进批次分支并提交，项目根对应文件恢复为 `main` 状态；无关改动保留。方法指纹变了时，它会跑一次方法自测和基线门禁。
4. 在聊天里给用户的启动命令（由用户执行）：

   ```bash
   cd "/Users/Admin/Desktop/personal agent" && /Users/Admin/Desktop/loop/bin/loop 启动 "/Users/Admin/Desktop/personal agent-dev分支/docs/batches/<批次>/批次.json"
   ```

   上面是当前固定开发空间的写法，以开工实际打印的命令为准；协调方替换批次名后给用户完整命令。单段直接开会话；多段交给流水线，按 `steps` 执行，最后跑整批 e2e；并行批次仍须用户授权。给用户之前先用 `--dry-run` 核对。
5. 运行中查状态：用开工输出里的 `状态` 命令，批次文件同样取开发空间那份。只读核对时加 `--dry-run`，避免普通状态查询触发队列恢复。

## 合入（每批）

用户说「合入」后，协调方执行：

```bash
cd "$P" && git status --short
/Users/Admin/Desktop/loop/bin/loop 合入 "/Users/Admin/Desktop/personal agent-dev分支/docs/batches/$B/批次.json" --dry-run
/Users/Admin/Desktop/loop/bin/loop 合入 "/Users/Admin/Desktop/personal agent-dev分支/docs/batches/$B/批次.json"
```

批次文件路径以开工输出为准。已登记的批次由合入队列先测试，`合入` 只发布测试通过的固定候选，不再现场重新合并或提交开发空间；未登记的旧批次才走兼容合并入口。项目根无关改动及暂存状态由程序保存、恢复；有重叠或冲突就停下报告。暂不推送 `origin`，开发空间和分支保留，不自动清场。

## 更新 Loop 接入（协调方执行）

1. 核对 `/Users/Admin/Desktop/loop` 当前提交和相关使用说明。项目直接调用该目录，不复制一套 Loop 程序；旧文档中的提交号不能当成实际加载版本。
2. 运行官方接入命令更新可变写法；已有项目配置保持原样，`CONVENTIONS.md` 不手改：

   ```bash
   node /Users/Admin/Desktop/loop/setup-acceptance.ts "/Users/Admin/Desktop/personal agent" --host codex --yes
   ```

3. 核对宿主插件缓存与 Loop 的 `plugins/autoreview/hooks/hooks.json` 是否一致，并核对实际会话是否收到提示。新版在写提示词、方法或配置，以及调用 `bin/loop` / `bin/pi-dev` 时按需指向权威规则；写配置时还会校验。它不自动改项目启动说明、迁移流程或替用户开启自动合入。
4. 缓存、信任或实际加载落后时，按 Loop [README「生产 Loop：按动作指路与即时校验」](../../../loop/README.md#生产-loop按动作指路与即时校验)的当前部署说明更新，并给用户完整操作步骤；已经生效则不重装。将核实结果写回基线，区分文件一致、信任已登记与当前会话实际触发。
