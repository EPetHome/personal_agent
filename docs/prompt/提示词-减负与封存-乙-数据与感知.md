# 提示词：减负与封存 · 乙段 数据与感知（闭环 1 修复）

依据：需求书 `docs/requirements/需求书-personal-agent.md` D27 的 2026-10-28 补充；问题单（真机数据与因果链，先读）[运行数据只增不减](../../iusses/运行数据只增不减.md)、[一个打开就关掉的 Codex 会话，让整个 Codex 盯防「看不见了」](../../iusses/空的Codex会话让整个Codex看不见.md)（「只影响那一个会话」部分）。甲段已在同一分支上改过发卡时机和卡片，本段在其之上做。

## 目标

运行数据不再只增不减，检测也不随日志变长而越跑越慢；一条报信对不上，不再让整个工具看不见。

现在：会话每变一次，就把整份会话记录再追加进事件日志（`code/src/core/agent.ts` 约 173 行 `session_observed`），这类事件占日志 84%（真机 46 MB 中 40.5 MB）；日志没有保留期限；每轮检测要把整份日志从头读、重放多次（`agent.ts` 约 166、244、252、259、265 行，`code/src/core/store.ts` 的 `readEvents`）。推送对不上时把错误记到整个来源（`agent.ts` 约 214 行），来源一有错误，这个工具的所有会话都不再确认状态。

## 已拍板

- **只记变化**（用户 2026-10-28 认同）：会话变一次只记变了的部分，单次记录的大小不随会话变长而变大；读回来时能还原出和现在一样的会话记录。
- **封存**（用户 2026-10-28 认同；天数按协调方建议）：**7 天前** 的事件压缩归档成单独的归档文件，**永久保留、不删**；日志里只留「封存时的状态」加之后的新事件；每轮检测只读这两样，不再读归档。归档内容和原事件逐条一致，可以解压还原。封存写到一半失败，原事件一条不丢，下次重来。
- **迁移**：升级后第一次运行时，先把整个数据目录备份一份（与现有备份命名风格一致），再对现有日志做第一次封存。结果里写清恢复办法（用备份整目录替换，或用归档还原日志）。
- **临时文件**：启动时清掉写状态时残留的临时文件（真机现有 3 个 `.state-*.tmp`）。人工建的升级前备份目录由协调方运维时清理，代码不碰。
- **对不上只影响那一个会话**：一条报信和会话对不上时，只把那一个会话标成「看不见了」并提醒；同一工具的其他会话照常判断、照常提醒。真正读不了目录、核心信号整体取不到时，仍按现有规则判整个来源看不见（D29）。
- 统计、总览、每周小结、复盘、反馈生效（误报压制等）在封存前后结果一致。

## 验收标准

A1. 操作：一个长会话（1000 步）和一个短会话（10 步）各变化一次
    预期：两次新增的事件大小相差不超过 2 倍
A2. 操作：放入从 8 天前到今天的事件，触发封存
    预期：7 天前的事件进了压缩归档，日志里没有它们了；归档解压后和原事件逐条一致
A3. 操作：封存后跑检测、要总览、看每周小结
    预期：会话状态、总览、小结都和封存前一致
A4. 操作：封存写到一半中断，再跑一次
    预期：原事件一条不丢，下一次封存成功
A5. 操作：拿一份改前格式的数据目录升级
    预期：升级前自动整目录备份；升级后状态和升级前一致；结果里有恢复办法
A6. 操作：数据目录里放 2 个残留的状态临时文件，然后启动
    预期：临时文件被清掉，其他文件不动
A7. 操作：一条 Codex 报信对不上，同时另一个 Codex 会话停在等你
    预期：只有对不上的那个会话标「看不见了」；另一个照常发「在等你」
