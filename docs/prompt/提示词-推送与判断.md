# 提示词：推送与判断（闭环 1 第二批 · 段 1）

## 目标

personal agent 的闭环 1「AI 工作盯防」已经能只读感知四个来源，按规则判断状态，并把提醒写进文件发件记录（代码在 `code/`，用法见 `code/使用说明.md`）。本段补上三样东西：

1. **推送**：给 Claude Code、Codex、Pi 各做一个只负责通知的钩子 `message-listener`，让「在等我」能马上知道。
2. **判断**：用模型判断「疑似跑偏」和「做完了还是在问你」。
3. **本机渠道与反馈**：「现在就要你」的提醒弹本机通知；用户可以用本机命令回「正确 / 误报 / 漏了」。

另外修掉上一批真实数据抽查发现的两类状态误判。本段做完后由 loop 程序提交，段 2「渠道与常驻」接着在这个提交上开工，会照本段定的渠道接口接飞书。

依据（都在运行版项目根，只读）：需求书 `/Users/Admin/Desktop/personal agent/docs/requirements/需求书-personal-agent.md` 的「第一个闭环」和 D21、D24；方案 `/Users/Admin/Desktop/personal agent/docs/prompt/方案-闭环1-AI工作盯防.md` 第 1、2、4、5、7、8、9、11 节（钩子事件对照、推送事件格式、模型调用、提醒格式都在里面）。

## 已拍板

- **钩子只通知、不改变工具行为**：钩子把事件按方案第 11 节的格式追加一行到推送目录的 `<工具>.jsonl`，然后立即退出，永远返回成功；不连网、不等中枢、不读会话内容。推送目录写不进去时也照样成功退出。中枢没在运行时，三个工具照常工作。
- **事件对照**按方案第 11 节：CC `Notification`（`permission_prompt`）、Codex `PermissionRequest`、Pi `permissions:ui_prompt` → `waiting_permission`；三家的 `Stop` / `agent_settled` → `turn_end`，`detail` 放最后一条回复；`SessionEnd` / `session_shutdown` → `session_end`。CC 的 `idle_prompt` 不单独成事件。CC 钩子设 `async`。
- **安装形态**：CC、Codex 仿照 loop 的本机插件（参考 `/Users/Admin/Desktop/loop/plugins/autoreview/` 和 `/Users/Admin/Desktop/loop/.claude-plugin/marketplace.json`）打包，不直接改用户的 `settings.json` / `hooks.json`；Pi 做成扩展。每个都有安装和卸载命令：安装前先备份要动的配置，卸载连插件登记一起移除，卸载后配置和备份完全一致。安装和卸载的目标位置（相当于用户主目录）必须能用参数指定。
- **模型是组件**：模型判断只通过一个「判断器」接口，输入是现拼的小上下文（意图原文、用户后来追加的要求、上次的「做到哪了」摘要、上次检查之后的新步骤），输出只有「是 / 否」和依据。第一版实现调用 `pi -p --no-tools --no-session --no-extensions --no-context-files --mode json`，模型 `opencode-go/deepseek-v4.1-flash`；可执行文件和模型都来自配置。不给模型任何工具。
- **疑似跑偏**：只答是或否。答「是」必须指出对不上的那句意图和那一步，指不出就按「否」处理。同一会话跑偏检查最小间隔 10 分钟，有新动静才调。属于「现在就要你」。
- **做完还是在问你**：助手答完、没有未返回的工具时，问模型「它是在等你回复吗」，只答是或否：「是」判「在等我」，「否」判「已完成」。
- **用量与失败**：每日调用有上限（可配置）；超了或模型调用失败，就只用规则判断，并在总览里标出。模型判出来的提醒，一句话里带「可能」。
- **评测集**：做一个评测命令，读一个样本目录，每份样本给出意图、追加要求、最近几步和期望答案，用当前配置的判断器分别按「只答是或否」和「高 / 中 / 低」两种问法各跑一遍，输出各判对几份；只记录，不设通过线。样本由协调方另编，格式由你定，写进使用说明。
- **本机渠道**：建一个统一的渠道接口，做两件事：发一条带内部编号的提醒；收回复（编号加内容）。本机渠道照这个接口实现：「现在就要你」用系统自带的 `osascript` 弹通知，通知的可执行命令来自配置；「有空看」不弹本机通知，只写发件记录。现有的文件渠道保留。
- **反馈**：本机命令接收「正确 / 误报 / 漏了」，可以附一句话；不指定编号时默认指最近一条提醒；回复「已记下」；`feedback.jsonl` 里每条带日期，并指向那条提醒。「漏了」可以不指向提醒。给人看的文字里不出现内部编号。
- **修两类误判**（上一批真实数据抽查发现的）：① Pi 助手消息 `stopReason` 是 `error` 或 `aborted` 时，里面带的工具调用不算没返回；② Codex 一轮 `task_complete` 之后才完成的后台命令（`item_completed`），不把这轮重新算成没结束。
- **组件说明**：每个来源、渠道、钩子组件的「说明.md」补上「能让它做什么」一栏，第一阶段都写「无」。

## 验收标准

A1. 操作：把 CC 钩子装进一个临时主目录，再用一份「`Notification`，`notification_type=permission_prompt`」的事件输入去执行这个钩子
    预期：钩子退出码为 0；推送目录的 `cc.jsonl` 多一行 `waiting_permission`，带会话号、项目目录、原件路径和时间
A2. 操作：分别对 Codex 钩子输入一份 `PermissionRequest`，对 Pi 扩展触发一次 `permissions:ui_prompt`
    预期：`codex.jsonl`、`pi.jsonl` 各多一行 `waiting_permission`，字段和 A1 相同
A3. 操作：把推送目录设成不可写，再依次触发三个工具的钩子
    预期：三个钩子都在 1 秒内以退出码 0 结束，没有输出报错
A4. 操作：在临时主目录里装上三个钩子，再执行卸载，比对配置文件和安装前的备份
    预期：完全一致，插件登记也已移除
A5. 操作：放入一条编的 CC `waiting_permission` 推送事件和对应的会话样本，跑一轮检测
    预期：发件记录多一条「现在就要你」的「在等你」提醒，写有工具名、项目目录、意图一句话、做到哪了、在等我做什么；本机通知的测试替身收到一次调用
A6. 操作：放入一份编的会话样本，意图是「只改 A 文件」，之后一直在改不相关的 B 模块；判断器替身答「是」并指出意图原句和那一步，跑一轮检测
    预期：发件记录多一条「疑似跑偏」提醒，写明意图是什么、实际在做什么、对不上在哪里
A7. 操作：同 A6，但判断器替身答「是」却没有指出意图原句
    预期：不发「疑似跑偏」提醒
A8. 操作：放入一份助手已答完、没有未返回工具的会话样本，判断器替身先答「是」跑一轮；换一份同样的样本，替身答「否」再跑一轮
    预期：第一份发「在等你」提醒；第二份在总览里是「已完成」，不发提醒
A9. 操作：对最近一条提醒执行本机反馈命令，回「误报」并附一句话
    预期：输出「已记下」；`feedback.jsonl` 多一条带日期、指向那条提醒的记录
A10. 操作：分别放入两份编的会话样本：Pi 一条助手消息 `stopReason=error` 并带工具调用，之后重试答完；Codex 一轮 `task_complete` 之后才来一条后台命令完成记录。跑一轮检测
    预期：两个会话在总览里都是「已完成」
