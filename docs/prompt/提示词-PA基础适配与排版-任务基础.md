## 目标

在 Loop 登记的本任务开发空间里，完成 PA 的真实任务/执行身份、旧记录兼容，以及本机最新 Loop 第 3 步协议适配。让已授权工作能被正确查询、关联、派出一次、更新和按原身份控制，为下一批已派出卡提供基础。本批不交付已派出卡，不开放真实 PA 派 Loop 体验。

读取顺序：本提示词 → 同批[整批验收标准](../batches/PA基础适配与排版-20261107/整批验收标准.md) → [分批方案](方案-PA分批推进.md) → [主需求](../requirements/需求书-PA-LangGraph重建.md)的任务、权限、留痕要求 → 受影响源码。Loop 的当前协议读取 `/Users/Admin/Desktop/loop/工具清单.md` 开头、第 3 步 `development-card.ts/kernel-cli.ts/kernel.ts/node-ledger.ts`，旧文档下半部只作历史。不要修改 Loop 项目。

## 已拍板

- 派单就是用户的一件真实任务；项目是归属/授权资源的索引；执行是原工具的具体运行。复用现有 Store、任务、来源关联、WorkerJournal、消息及检查点，不重写系统、不新增第二本任务账。小事不强制建项目。
- PA 自派和本人独立启动但已授权的 Loop 都保留真实来源；原运行、批次、任务、节点、重试不得混为一个身份。必须理解新版多任务 `tasks`，一项等待不冒充全批都暂停，一项完成不冒充整批完成。新派工先支持单任务开发卡，不建设通用编排器。
- 使用新版 `version:1` 开发卡和 `kernel:1` 查询/回执；不用旧开工、固定工作区、stages/steps、送话 --stage 或续跑 --id 控制新卡。实际支持的查询/启动/停止/续跑分别核对；接口不支持的动作明确不可用，不改用 shell 猜测或伪造回执。停止整批与停止某任务必须保留本人指定对象，不能扩大到整批。
- 任务身份由获准项目的可核对仓库身份和来源运行/任务身份建立，不按标题、同名目录、PID 单值合并。最新记录修订可从获准且绑定的 ledger 抽取必要字段，不能把整个内核目录或全部会话给模型。
- 先保存原操作身份再产生副作用；启动派发、宿主接收、实际执行、技术检查、发布、业务验收分别记录。未知不重派；重复输入、重启和迟到记录不重放，不把旧状态覆盖新状态。新卡的“可合入/已合入”不等于全部验收通过，读取本地/远端发布事实及缺项。
- 只把已经绑定执行的普通记录变化接到现有来源更新路径；支持范围及最后核实时间可查。整个来源的新任务自动发现、长期关注、无事件异常检测、渐进上下文和独立 Pi 接入留后续。本批不采用此前 B2 的 10/60/90 秒提议值。
- 旧派单、操作编号、来源关联、消息、检查点、未决确认保留；能兼容加字段就不重建表。需要迁移则提供备份/恢复方法，先在构造库验证；无法关联的旧记录保持未核实/控制不可用，不清空、不猜映射、不重发。实际数据迁移仅在以后获准部署时做。
- 本人明确普通委托沿原确认规则；权限、deny、暂停/取消和重复动作保护不降低。已有 Pi 办公任务不增加 Git 或代码评审前置。普通派工不得产生提交到 dev、远端推送、部署或真实账号操作。
