# 全新 PA 乙：底座和托管 loop

本批共 6 段，这是第 2 段，接在「甲 减法」之后。先读[六段共同约定](../batches/全新PA-20261102/共同约定.md)。

## 目标

loop 卡都是核实过、带方案的，点按钮就能回话。对应[方案](方案-全新PA.md)第 1、3、16 项，第 4 项里的送话，第 15 项的记录。

1. **账本**：事件（只追加）→ 线索 → 事情（意图卡，有版本，可挂上级事情，子卡继承总目标）⇄ 派工；待你决定、待发、待写、留痕、观测记录都在账本里。状态只存这里，重启从账本恢复。
2. **事件驱动**：拆掉每 2～3 分钟一轮的大循环；loop 事件一到就处理，另加 10 分钟一次的低频巡检兜底。
3. **托管 loop**：读收件目录 `loop/<批次名>.jsonl` 里的事件（格式见方案附件 1），按 `id` 去重；需要时查状态（附件 2）、只读证据。用 loop 事件取代上一段保留的「读 loop 总结出卡」。
4. **先核实再叫**：停下的状态过 3 分钟还停着才算停；「恢复」在这之前到了就不发卡。核实 loop 报的原因和证据，对不上时卡片两样都写（「loop 说是磁盘不足，核实是测试失败」），并记一次 loop 误报。「做完」要在批次分支或合入候选上找到报的提交；loop 还没做「一批一次提交」时，核实候选提交并写明「还没提交到分支」。
5. **闸门**：需要你决定、暂停、返修到上限、做完马上推；合入队列前两次退回和停滞进「等你」清单，不推。同一批次始终是同一张卡在更新。只由 PA 发通知（loop 自己的通知开关是 loop 那边的事，本段不管）。
6. **卡片**：核实过的事实 + 方案（写依据）+ 按钮。
7. **送话**：按建议、选项、我写一句、继续、再给一轮。先记、再送、等回执；回执「已送到 / 已读」更新原卡；「说不清」标不确定，不重发；同一请求号只投一次。送话前过围栏：只能指向明确的那条派工。
8. **围栏**：红线、不许读、档位（本段只有「建议」一档在用）、留痕、撤回的骨架，后面各段的执行、派活、自动档都从这里过。
9. **观测记录**：叫了几次、核实后没叫几次、按建议的比例、loop 误报、查询花费，只记不推。

## 已拍板

- 「按建议」只确认紧跟的这一条；红线类照样给建议，但不给一键，按钮写明确认的是什么。
- 研判（核实、出方案）用只读 Pi，想完就退；沿用现有只读工具和读取拦截。
- 账本是新结构：结果里写清数据文件在哪、怎么备份和恢复。

## 边界

- 推送、合入、停批次的按钮是下一段的事，本段不做。
- 飞书打字、派活是第 4 段的事，本段不做。

## 验收标准

A1. 操作：替身 loop 写一条「开始」事件
    预期：10 秒内账本里出现这个批次的事情和派工（不等巡检），不发卡
A2. 操作：替身写「需要你决定」，带问题和两个选项；3 分钟后仍停着
    预期：假飞书渠道（`feishu.mode` 为 `fake`）收到一张卡：问题原文、建议及依据、按钮
A3. 操作：替身写「暂停」，2 分钟后写「恢复」
    预期：不发卡
A4. 操作：替身写「暂停：磁盘不足」，给的日志里其实是一条测试失败
    预期：卡片写明「loop 说是磁盘不足，核实是测试失败」
A5. 操作：在 A2 的卡上点「按建议」
    预期：替身收到的话和建议原文一字不差；留痕里有这次送话；回执「已读」后原卡更新为已送达
A6. 操作：送话时替身回执「说不清」
    预期：原卡标「不确定」，替身没有收到第二次
A7. 操作：替身写「做完」，但批次分支和候选里都找不到它报的提交
    预期：卡片写明「说做完了，没找到提交」
A8. 操作：同一批次先后写「暂停」「恢复」「做完」
    预期：飞书上始终是同一张卡在更新
A9. 操作：发卡后重启 PA
    预期：账本里的事情、派工、卡片状态都还在，旧卡不重发
A10. [人工] 操作：看「需要你决定」「暂停」「做完」三种卡
    预期：文案和方案是你想要的
