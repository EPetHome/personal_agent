# 提示词：误报修复（闭环 1 第四批）

问题单：[CC 推送对账误报「看不见了」](../../iusses/CC推送对账误报看不见了.md)

## 目标

闭环 1 已经装在用户电脑上运行，下一步是让用户连续用一周。现在误报太多，用户会因此不再信任提醒。本批修掉其中两类会反复出现的误报，再补上飞书连不上时的原因记录（马上要接真实飞书）。修完后接开机自启和飞书，开始试用。

| # | 真机上看到的现象 | 原因（协调方读源码推断，开发方以实际代码为准） | 要修成什么样 |
|---|---|---|---|
| 1 | 用户在 CC 会话里中途 `cd` 进子目录（例：会话从 `/Users/Admin/Desktop/IDaaS` 开始，后来 cd 进了它下面的一个子目录），此后这个会话的每条推送都「对不上」，马上报「Claude Code 的盯防看不见了」，而且一直挂着 | CC 来源把会话的项目定为会话文件里第一条记录的 `cwd`（`code/src/sources/cc/index.ts`）；推送里的 `cwd` 是推送当时的目录（`code/src/core/perception.ts` 的 `parsePush`）；对账要求会话号、项目、文件路径三者都相同（`code/src/core/sessions.ts` 的 `pushMatchesMember`），项目不同还被当成「错项目冲突」，不给宽限（`code/src/core/agent.ts` 的 `detect`）。判断「在等你」和模型检查也用同一个对账函数 | 推送的会话号和文件路径都对得上，推送里的目录又在这份会话文件里出现过，就算对上了，不报「看不见了」。对上以后，这条推送照常参与「在等你」等判断 |

## 已拍板

- **总览里会话的项目**：仍按会话起始目录显示，不因中途 cd 改变；同一个会话不因换目录拆成两行。
- **错项目保护不放宽**：会话号对不上、文件路径属于另一个会话，仍然马上按「看不见了」报，和现在一样。
- **目录还没写进会话文件时给宽限**：推送的会话号和文件路径都对得上，但推送里的目录还没出现在会话文件里时，不要马上判冲突，按推送早到的规则给最多 2 轮宽限；宽限后还没出现，再按错项目报「看不见了」。
- **空会话认得要严**：同时满足这三点才算空会话——推送是「会话结束」；这个会话号以前从没在任何会话文件里出现过；宽限后文件仍不存在。以前读到过、后来文件不见了的会话，照旧报「看不见了」。「在等你」「一轮结束」推送对应的文件宽限后仍不存在，照旧报「看不见了」。
- **宽限不变**：仍是不超过 2 轮检测。
- **已经报出的误报要能结束**：用户电脑上的数据目录里已经有第 1、2 类推送和因此报出的「看不见了」，也有 loop 验收会话的「跑偏」记录。换上新代码后，第 1、2 类推送按新规则不再算对不上，「看不见了」照现有的恢复逻辑结束；loop 自己的会话从总览里消失。都不重复提醒，不删已有记录。
- **三个工具规则一致**：第 1、2、3 条对 CC、Codex、Pi 都适用。

## 边界

- 只改 `code/` 和本批结果 `docs/batches/误报修复-20261026/结果.md`。不新增第三方运行依赖。
- 不读写真实的 `~/.claude`、`~/.codex`、`~/.pi`、`~/.pi-autoreview`、`~/.personal-agent`。门禁、测试和自动验收只用构造的会话样本、推送事件和飞书替身，不调用真实模型，不连真实飞书，不弹真实通知。已有场景样本目录（`docs/batches/*/samples/`）只读。
- 已有行为保持不变（已有测试全部通过）：推送比会话文件早到时的两轮宽限、首次接入不补发、超过 24 小时算已搁置、提醒去重、每日调用上限、真机修复批的全部修复。
- 运行数据只追加：不改写、不删除已有的事件、发件和反馈记录；新增字段或事件时，旧记录照样能读。
- 不做：开机自启和飞书接入本身（由协调方在真机上操作）；跑偏判断的准确度；评审提过的其余小问题；钩子安装与卸载。

## 验收标准

A1. 操作：放入一份 CC 会话样本，前几条记录的 `cwd` 是 `/demo/shop`，后面的记录换成 `/demo/shop/api`；再放一条这个会话的「在等你」推送，`cwd` 是 `/demo/shop/api`，最后一条助手消息在问用户问题；跑一轮检测
    预期：发出这个会话的「在等你」提醒；不发「看不见了」；总览里这个会话只有一行，项目是 `/demo/shop`
A2. 操作：放入一份 CC 会话样本，所有记录的 `cwd` 都是 `/demo/shop`；放一条这个会话的推送，`cwd` 是 `/demo/shop/api`；跑一轮检测，再在会话文件末尾追加一条 `cwd` 为 `/demo/shop/api` 的记录，再跑一轮
    预期：两轮都不发「看不见了」；第二轮这条推送对上了
A3. 操作：放入一份 CC 会话样本，所有记录的 `cwd` 都是 `/demo/shop`；放一条这个会话的推送，`cwd` 是 `/demo/other`；连跑三轮检测
    预期：发出「看不见了」提醒
A4. 操作：只放一条 CC「会话结束」推送，它指向的会话文件一直不存在，这个会话号也没在任何会话文件里出现过；连跑三轮检测
    预期：三轮都不发任何提醒；总览里没有这个会话；检测记录里能查到这条推送被当成空会话
A5. 操作：放入一份 CC 会话样本跑一轮检测，然后删掉这个会话文件，再放一条它的「会话结束」推送；连跑三轮检测
    预期：发出「看不见了」提醒
A6. 操作：放入一份 Pi 会话样本，会话号以 `autoreview-acc-` 开头，内容是一段会被判成跑偏的操作；再放一份普通 Pi 会话；判断器替身对所有调用都答「跑偏」；跑一轮检测
    预期：只对普通会话发「疑似跑偏」；总览里没有那份 `autoreview-acc-` 会话；判断器替身没收到它的调用
A7. 操作：准备一个数据目录，里面已有 A1 那样换过目录的推送、因此记下的「看不见了」，以及一份 `autoreview-acc-` 会话的「疑似跑偏」记录；换新代码后跑一轮检测
    预期：「看不见了」结束；不再发新提醒；总览里没有那份 `autoreview-acc-` 会话；之前的事件、发件记录一条都没少
A8. 操作：用飞书替身让长连接启动时报「凭证不对」，启动常驻跑一轮
    预期：常驻日志里有一条飞书连接失败的记录，写明是凭证问题；日志里没有凭证内容；总览里显示飞书没连上
A9. 操作：对 Pi、Codex 各做一遍 A1 和 A4
    预期：结果和 CC 一样
A10. [人工] 操作：换上新代码后在真机上正常用一天，包括在会话里 cd 进子目录、打开 CC 马上关掉、跑一批 loop
    预期：不再收到这几类误报
