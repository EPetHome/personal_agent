# 提示词：减负与封存 · 丙段 失败留痕（闭环 1 修复）

依据：问题单（真机事实，先读）[检测偶发失败，原因不落记录](../../iusses/检测偶发失败不留原因.md)、[模型每日额度上午就用满](../../iusses/模型额度上午就用满.md)「还剩」一条；需求书「没发出去的提醒（去重、额度用完）在总览里标出」。甲、乙段已在同一分支上改过发卡和数据，本段在其之上做。

## 目标

出错时留下原因、及时停手、告诉用户，不再「静默失败、无限重试」。真机上有一张 10-27 的卡片发飞书失败了 654 次以上，用户一直不知道；检测失败只写「检测未完成」；磁盘写满导致服务崩溃时没有任何提醒。

现在：渠道发送 `catch { ok = false; }` 不记原因、没有次数上限（`code/src/core/agent.ts` 发送循环）；检测失败只记固定一句（`code/src/service/daemon.ts` 约 76 行）；已有的失败分类可复用（`code/src/core/failures.ts` 的 `safeProcessingFailure`，含 `storage_full` 等）；模型失败已有 `failure` 分类，不用再改。代码里模型每日上限默认 240（`code/src/core/config.ts`），用户 2026-10-27 定「根本就不要卡」。

## 已拍板

- **渠道发送失败**：每次失败记原因类别（超时、连接、被飞书拒收等，按现有分类方式），不写凭证、原始报文和正文。同一张卡在同一渠道**连续失败 5 次**就停发（值按协调方建议）；中间有一次成功就只算发出一次，不重复发。
- **告诉用户**：停发后弹一次本机通知，写明哪张卡（标题）没发到哪个渠道、原因类别；总览里标出这张没发出去；同一张只提醒一次。
- **历史欠账**：升级前已经连续失败超过上限的卡（真机那张 600 多次），升级后直接按停发处理，提醒一次，不再重发。
- **检测失败**：服务日志的检测失败记录带原因类别（复用 `safeProcessingFailure`）。
- **异常退出**：启动时发现上次运行没有正常停止，在服务日志记一条「上次没有正常停止」（能拿到原因类别就带上）；已有的「短时间反复重启」告警不变。
- **磁盘写满**：检测或写入因磁盘已满失败时，弹本机通知提示磁盘已满、盯防可能停了；同一次连续失败只提醒一次，恢复后可再次提醒。
- **模型每日上限**：配置里不写时默认不限次数（不再默认 240）；写了照旧生效。
- 数据只追加；旧记录缺新字段照常读。

## 验收标准

A1. 操作：飞书替身对一张卡每次都返回失败，连续跑检测
    预期：每次失败记下原因类别（不含凭证和原始报文）；失败满 5 次后不再重发
A2. 操作：同 A1，停发之后
    预期：弹一次本机通知，写明哪张卡没发到飞书和原因类别；总览里标出这张没发出去；之后不再重复提醒
A3. 操作：飞书替身前 2 次失败、第 3 次成功
    预期：飞书只收到一次这张卡；不弹「没发出去」的通知
A4. 操作：拿一份数据目录升级，其中一张卡历史上已连续发飞书失败几百次
    预期：升级后不再重发它，只按 A2 提醒一次
A5. 操作：构造一个会让检测出错的输入，跑检测
    预期：服务日志里这次检测失败的记录带原因类别
A6. 操作：服务被强行结束后重新拉起
    预期：服务日志记下「上次没有正常停止」
A7. 操作：构造写入时磁盘已满，跑检测
    预期：失败原因类别是磁盘已满，并弹一次本机通知提示磁盘已满
A8. 操作：配置里不写模型每日上限，连续跑检测
    预期：模型调用不受次数限制
