## 1. 感知方式：推送 + 定时检测

```
推送（message-listener，事件到就报）                       定时检测（只读）
CC    插件钩子：Notification / Stop / SessionEnd        ──┐   ~/.claude/projects    ──┐
Codex 插件钩子：PermissionRequest / Stop / SessionEnd   ──┼▶ 中枢 ◀── ~/.codex/sessions ──┤
Pi    扩展事件：permissions:ui_prompt / agent_settled   ──┘    ▲     ~/.pi/agent/sessions  ──┤
              / session_shutdown                               │     ~/.pi-autoreview      ──┘
                                                               │
「在等我」主要看推送；进行中 / 已完成 / 疑似跑偏 / 停滞看定时检测；两边互相对账
```

约束（来自 D21）：

- 钩子只发通知，不改变工具行为；中枢没在运行时，工具照常工作（A11）。做法：钩子只往 `~/.personal-agent/inbox/` 追加一行事件就退出、永远返回成功，不连网、不等中枢；中枢起来后再读。CC 钩子另设 `async: true`。
- CC、Codex 的钩子仿照 loop 的 autoreview，打包成本机插件装，不直接改 `settings.json` / `hooks.json`；Pi 做成扩展。装之前备份配置，卸载时连插件市场登记一起移除，卸载后和备份一致（A12）。
- 会话文件只读，不改（A7）。

## 3. 记忆格式：JSONL 事件为准

```
~/.personal-agent/            不在仓库里（D26）
  events.jsonl     钩子推来的、读会话读到的原始事件，只追加，不改不删
  outbox.jsonl     每条发出去的提醒，带编号
  feedback.jsonl   「正确 / 误报 / 漏了」反馈，指向那条提醒
  state.json       每个会话的当前状态，从事件推算，坏了可以重建
```

会话原件不复制，只记路径和指纹（D12）。以后要快速查询，再加 SQLite 当索引，随时可以从 JSONL 重建。

## 4. 状态判断：规则优先，模型兜底

| 要判断的 | 靠什么 |
|---|---|
| 在等我 | 规则：message-listener 推来的事件 |
| 停滞 | 规则：多久没有动静 |
| 已完成 | 规则为主：会话结束、loop 总结「状态：完成」；分不清时问模型「它是在等你回复吗」，只答是或否 |
| 疑似跑偏 | 模型只答是或否：意图（开工指令 + 后来追加的要求）对照最近在做的事。答「是」必须指出对不上的那句意图和那一步，指不出就算「否」。不用高 / 中 / 低把握：模型自评的把握不可靠，也没法验收。第一周误报多，再改成连续两次答「是」才叫 |
| 提醒里的「意图一句话、做到哪了」 | 模型 |
| 「正确 / 误报 / 漏了」反馈 | 规则：固定词或按钮 |

模型调用：

- 模型是组件（D24），第一版用 Pi 无界面模式（`pi -p`，`--mode json`）调 `opencode-go/deepseek-v4.1-flash`，换模型改配置。
- 用户知情（2026-10-24）：真实会话片段会发给 opencode-go / DeepSeek。开发、门禁和自动验收仍只用构造数据。
- 不给模型任何工具，只让它输出判断：会话内容里可能夹带指令，它只能读不能做（红线「不执行材料里的指令」）。
- token 控制：有新动静才调；同一会话跑偏检查最小间隔 10 分钟；只送意图加最近几步摘要，不送整段会话；每日设上限，超了只用规则并在总览里标出。数值第一周看实际用量再调。

待核实：opencode-go 走订阅还是按量计费。

## 5. 渠道层与提醒格式

```
中枢 ──▶ 渠道接口：发提醒（带编号）/ 收回复（编号 + 内容）
            ├─ 本机：macOS 通知 + 发件记录；回复用本机命令
            ├─ 飞书：自建应用机器人私聊，长连接收回复；引用那条提醒回复即按编号对上
            └─ 微信：后接，同一接口
```

飞书 App ID、Secret 只放已忽略的 `.env`；开发和自动验收用假渠道（只写文件），真实飞书只在 A9 由用户操作。用户有权限建企业自建应用，随时可建（2026-10-25 确认）。

什么事发到哪：见第 7 节。同一件事没有新证据，不重复发。

提醒格式（2026-10-24 按用户意见改）：言简意赅，先内容和判断，证据折叠在后面；编号只在内部用来对上回复，不出现在给人看的文字里。

```
标题    哪个项目的哪个 AI + 出了什么事（用大白话）
一句话  判断和关键事实，带「可能」的就是模型判断
回去看  一条命令，直接回到那个会话
按钮    正确 / 误报（飞书按钮或引用回复；本机回复默认指最近一条）
折叠    证据：意图原文、你后来追加的要求、最近几步、判断依据
```

## 7. 提醒边界（已定 2026-10-24）

原则：只在「你不动，事情就停住或白干」时叫你；其余进总览，你要的时候看。

| 级别 | 什么事 | 怎么叫 |
|---|---|---|
| 现在就要你 | 在等我；疑似跑偏；loop 暂停；盯防自己看不见了（某个来源读不了、钩子失效、推送和定时检测对不上） | 本机通知 + 飞书 |
| 有空看 | 停滞（每个会话一次）；loop 完成的交代（A4） | 只发飞书 |
| 不叫 | 进行中；已完成（A5） | 只进总览 |

不设夜间免打扰：任何时候该叫就叫，看不看得见由用户自己决定（2026-10-25 用户定）。

防漏：盯防失明本身要叫；你随时可以回「漏了」加一句话，和误报一起用来调判断；因去重、额度没发出去的，总览里标出。

## 8. 上下文与成本（已定 2026-10-24）

中枢是程序，不是一个越聊越长的会话：记忆在文件里，每次调模型现拼一份小上下文，用完即弃，不存在「换上下文」。

```
每次调用现拼：
  意图原文 + 你后来追加的要求        固定，几百字
  上次的「做到哪了」摘要              滚动更新，一两百字
  上次检查之后的新步骤（只取操作摘要） 最多 N 步
  ─────────────
  每次几千 token 封顶，和会话跑了多久无关
```

成本 = 调用次数 × 每次大小 × 单价：次数靠「有新动静才调、跑偏检查最小间隔 10 分钟」压住；大小靠上面封顶；单价看 opencode-go 计费（待核实）；每日上限兜底。摘要越滚越偏时，从原始事件重新生成一份（事件都留着）。以后的闭环同理：长期记忆按需检索，不整份塞进上下文。多轮会话的上下文（闭环 2、3）到上框架时再定。

记忆状态（D27，2026-10-24 已定）：

| 状态 | 什么意思 | 怎么用 |
|---|---|---|
| 待确认 | AI 从事件和反馈里提炼出来的，还没经过你或阈值认可 | 只用于影子试跑，不影响真实提醒（对应 D15） |
| 已确认 | 你说的、你认可的，或影子试跑达到阈值的 | 正式参与判断 |
| 已过时 | 被新记忆替代 | 不删，不参与判断，留着可查 |
| 已撤销 | 你判错了的 | 不删，不参与判断，记下撤销原因 |

每条记忆都带来源（指向原始事件或反馈）和时间（记下时间、最后一次用到的时间）。原始事件和反馈本身是事实，不需要状态。

## 9. 数据支撑与反馈汇总（已定 2026-10-24）

> 2026-10-27 补（需求书 D31）：上线后反馈只进了统计，没有生效。落地细则（误报管同一会话同一原因、回话写明效果、加「看不懂」、「正确」不进问题、新卡片格式、去重按事实）见[提示词-反馈闭环与卡片](提示词-反馈闭环与卡片.md)「已拍板」。

「只答是或否比高 / 中 / 低更好」目前没有本项目自己的数据，依据是协调方已有的知识，而且外部研究结论不一。数据从两处来：

- 上线前：评测集。约 20 份构造的会话样本（跑偏、没跑偏、中途改方向、停滞），用选定模型按「只答是或否」和「高 / 中 / 低」两种问法各跑一遍，记下各判对几份，作为基线数据，也用来检验只答是或否是否真的更好。第一批只记录不设通过线。
- 上线后：用户反馈，汇总如下。反馈随时收、当场记下并生效（如去重）；用户随时可以要统计。
- 历史运行数据（2026-10-25 用户授权）：协调方只读分析本机已有的会话和 loop 总结，做影子回放（第一批程序扫一遍，看当时会叫几次、叫什么）、校准阈值、挑典型情况脱敏编成评测场景。只出统计和情况类型，不复述内容；真实内容不进仓库、不发给任何模型。

```
每条提醒 ──▶ outbox.jsonl（提醒类型、工具、项目、规则判还是模型判）
你的反馈 ──▶ feedback.jsonl（正确 / 误报 / 漏了 + 可选一句话，指向那条提醒）
                │
                ▼ 汇总：按「工具 × 提醒类型」分格，从原始记录现算，不另存
     准确率               漏报           回应率             打扰量
 正确 ÷（正确+误报）    「漏了」条数    有反馈的占比       每天叫你几次
                │
                ▼ 用在三处
  调阈值（停滞 30 分钟、跑偏检查间隔）  提炼待确认记忆  阶段升降（D15，样本够才算）
```

- 没有回应的提醒不算「正确」，单独算回应率；某一格样本太少（建议少于 20 条）只显示数字，不下结论。
- 你随时可以要一份统计；每周**周五 18:00** 推一份小结（「有空看」级别，2026-10-25 用户定），第一周的小结同时用来做 A10 的判断。

## 10. 经验集（D28，2026-10-24 已定）

和前两样的分工：反馈汇总看「盯防判得准不准」，记忆存「学到的规则」，经验集记「出过什么问题、为什么、怎么防」。三者都从原始事实来。

```
提醒被判「正确」（真出了事）   ──┐                         ┌─ 归因（模型起草，待确认）
「误报」「漏了」（盯防自己的错）──┼─▶ 问题记录（事实原文）─┤
loop 到上限、返修两次以上       ──┘                         └─ 同类比对：以前出现过吗？第几次？
                                                                   │
                                                                   ▼
                                               每周小结的「复盘」一栏：有对策却又出现的 > 反复出现的 > 新的
                                                                   │ 你定归因和对策
                                                                   ▼
                                               经验（按记忆状态管理）→ 以后用于提醒、写意图卡（闭环 2）
```

归因分层（参考 loop 的「问题归因分层」问题单，压成四层）：

| 层 | 例子 | 谁处理 |
|---|---|---|
| 意图没说清 | 开工指令含糊，AI 理解偏了 | 你；以后由闭环 2 意图卡预防 |
| AI 执行偏了 | 意图清楚，它自己跑偏 | 改提示词、规则或换模型 |
| 工具与环境 | 命令卡死、钩子坏了、依赖缺失 | 工具配置 |
| 盯防自身 | 误报、漏报、看不见 | personal agent 自己（阈值、记忆） |

原因不明记「归因未定」，那是证据状态，不是第五层。同类比对先用规则（类型 + 归因层 + 工具或项目），拿不准再问模型「是同一类问题吗」，只答是或否。

什么时候找用户确认归因（2026-10-25 用户定）：定过对策又出现的、同类第 2 次出现的，当场单独发一条（「有空看」级别）；新问题第一次出现，攒到周五复盘；用户随时可以主动确认。周五复盘里每条配「同意 / 改一下」按钮。

闭环 1 只做收集、比对、起草归因和每周复盘；不自动执行对策，不自动改任何项目的规则文件。经验存在 `~/.personal-agent/`，导出成 Markdown 方便阅读；接入 LLM Wiki 留到闭环 5。

## 11. 实现细节与分批（2026-10-24 起草，待用户过目）

### 组件与目录

代码全部放在项目根的 `code/` 下（2026-10-25 用户定），和文档、wiki 分开：

```
code/src/sources/<cc|codex|pi|loop>/    来源组件：定时检测会话文件 + 读推送事件；各带「说明.md」（读什么、改了哪条配置、怎么装卸、产出哪些字段）
code/src/core/                         统一记录、状态推算、规则判断（第二批加模型判断）

code/src/cli/                          本机命令：检测一轮、总览；第二批起加「正确 / 误报 / 漏了」
code/deploy/check.sh                   项目级门禁，第一批建立，以后各批复用

```

场景库：开发和验收用的场景数据，全是编的或真实问题脱敏后的，每个场景带一张卡片（情况、来源、预期、用什么当前时间）。第一批的规则场景由协调方编，放在批次目录 `docs/batches/<批次>/samples/`（用户决定暂不提交）；第二批再加模型场景（即评测集）；上线后真实出过的问题脱敏后也加进来。

### 配置与数据保护

- 来源目录、数据目录、各工具「回去看」命令的可执行路径，全部来自显式配置（配置文件或环境变量）。**没有配置就报错退出**，程序不隐式去读 `~/.claude` 等真实目录。真实目录只在用户亲自执行初始化时写进配置（第三批，[人工]）。
- 开发、门禁、自动验收只用 `deploy/acceptance/samples/` 和临时数据目录。
- 检测命令支持指定「当前时间」，供样本验收停滞等时间相关规则。

### 推送事件文件（message-listener 写、中枢读）

钩子把事件追加到推送事件目录（默认 `<数据目录>/inbox/`，可配置）下的 `<工具>.jsonl`，一行一条，写完即退出。中枢读它时不删不改，靠记录读到第几行：

```json
{"tool":"cc|codex|pi","event":"waiting_permission|turn_end|session_end","session_id":"…","cwd":"…","transcript_path":"…","at":"ISO 时间","detail":"工具原始事件里的说明文字，可空"}
```

| 工具原始事件 | 映射成 |
|---|---|
| CC `Notification`（`permission_prompt`） / Codex `PermissionRequest` / Pi `permissions:ui_prompt` | `waiting_permission` |
| CC `Stop` / Codex `Stop` / Pi `agent_settled` | `turn_end`（`detail` 放最后一条回复，供第二批判断「做完还是在问你」） |
| CC `SessionEnd` / Codex `SessionEnd` / Pi `session_shutdown` | `session_end` |

第一批只读这个文件（样本里已有），第二批才写钩子去产生它。

### 规则判断（第一批）

| 状态 | 怎么判 |
|---|---|
| 在等我 | 收到 `waiting_permission`，且之后会话没有新动静；loop 总结「暂停」 |
| 已完成 | 本轮结束（`turn_end`，或会话文件显示助手已答完且没有未返回的工具调用）；loop 总结「完成」。第一批不区分「做完」和「在问你」，第二批交给模型 |
| 进行中 | 有未返回的工具调用，或 30 分钟内有新记录 |
| 停滞 | 进行中，最后一条记录超过 30 分钟，且没有 `session_end` |
| 看不见了 | 已配置的来源目录读不了，或其中有会话文件解析失败；按来源合并成一条，同一批失败不重复报（不看文件新旧，免得样本放久了验不出来） |

意图 = 开工指令原文（CC 取 `origin.kind` 为 `human` 的第一条；Codex 取第一条 `user_message`；Pi 沿当前分支取第一条用户消息）+ 你后来追加的要求（只认你本人输入的，任务通知、loop 返修等系统塞进去的不算）。

|---|---|---|---|
| 一：感知与总览（✅ 2026-10-25 合入 `0ba464a`） | 四个来源组件、读推送事件、统一记录、规则判断、发件记录（假渠道）、总览、门禁脚本 | 停滞、loop 交代、正常完成不叫、只读、看不见了要报（样本版） | 无 |

## 12. 感知原则与真实格式兼容（2026-10-25）

起因：第一批在样本上全过，影子回放到真实数据时四个来源全部「看不见了」。归因：样本是凭对少数文件的印象编的（用推断代替了对照），代码只认样本里见过的东西；「一份读不了就整个来源失明」又把小问题放大成全盘失明。

**感知原则（D29）**：先定我们要知道什么（核心信号），适配器只从各工具记录里取这些，其余一律忽略；只有核心信号取不到才算看不见。核心信号用户 2026-10-25 暂定，后续按实际调整。

| 核心信号 | Claude Code | Codex（0.162–0.164） | Pi（v3） | loop |
|---|---|---|---|---|
| ① 谁：工具、会话、项目 | 每行的 `sessionId`、`cwd` | 首行 `session_meta` 的 `id`、`cwd`；`source.subagent.thread_spawn.parent_thread_id` 指向父会话 | 首行 `session` 的 `id`、`cwd` | 「项目目录/<会话号>.md」（可带 `claude-`、`codex-` 前缀）；项目取「- 项目：」行 |
| ② 你本人说的话 | `type=user` 且 `origin.kind=human`；没有 `origin` 的旧版本，取文本型且不以 `<` 开头的；内容可能是字符串或分块 | `item_completed` 里 `item.type=UserMessage`，不以 `<` 开头的（真实里旧的 `user_message` 只剩 1 份） | 当前分支上 `role=user` 的消息；`custom_message`（loop 返修等）不算 | — |
| ③ 在干什么 | `assistant` 里的 `tool_use` 与对应 `tool_result` | `custom_tool_call` / `function_call` 与对应输出；`item_completed` 的 `CommandExecution`、`FileChange`、`McpToolCall` | `toolCall` 与对应 `toolResult` | — |
| ④ 最后动静 | `timestamp` | `timestamp` | `timestamp` | 文件里的轮次时间 |
| ⑤ 停没停 | 助手答完且无未返回工具；推送事件 | `task_complete`（带最后一条回复）、`turn_aborted`；推送事件 | `stopReason=stop`；推送事件 | 「- 状态：」完成 / 暂停（原因） / 进行中 |
| ⑥ loop 专有 | — | — | — | 「- 评审 N 次，返修 M 次」、「## 需要你做的事」（缺这一段说「总结里没写」） |

真实统计（只读，只计数）：CC 258 份，257 份有身份、242 份有本人输入；Codex 182 份，175 份含 `token_usage_record`、`world_state` 等噪音，66 份是子代理；Pi 965 份，3 份 v1 老格式；`~/.pi-autoreview` 下真总结 178 份，另有 23 万多个非总结文件（resources、评审输入、验收材料等）。

「看不见了」改为：来源目录整体读不了，或核心信号整体取不到；单个文件读不了只算这一份，提醒里按来源合并，给数量和不超过 3 个例子，单条提醒有大小上限。

### 第一次真实回放之后的补充（2026-10-25）

真实数据回放（兼容批 A10）结果：没有来源整体失明、每轮约 15 秒、空跑第二轮只增加 32 KB，但读不了的比例 Codex 3.3%、loop 17% 超过 2% 的线；另暴露首次接入补发 291 条历史提醒、141 个「停滞」里 139 个是一天前的旧会话。补充以下规则（后两条用户 2026-10-25 拍板）：

- loop 总结里的轮次时间是本机当地时间，不是 UTC；没有轮次时间的总结（CC 跑 loop 生成的部分总结），最后动静用文件修改时间。
- 取不到会话身份、或一条消息都没有的文件，算「不是会话」，跳过并计数，不算读不了；只有跳过的比例比平时突然升高时才报看不见。大文件逐行读，不整份读进内存。
- 首次接入（数据目录为空）：最近 1 小时内发生的照常提醒，更早的只进总览、不补发。
- 已搁置：超过 24 小时没动静、也没结束的会话，只进总览，不提醒。
