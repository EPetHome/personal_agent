# 全新 PA：整批验收标准

六段都做完后，在合起来的代码上跑一次，验的是各段接起来以后还成立。用编造的数据、替身 loop、替身 Pi 和假飞书渠道（`feishu.mode` 为 `fake`），怎么用见 `code/使用说明.md`。各段自己的验收标准在各段提示词里。

## 验收标准
A1. [甲-减法] 操作：放进一个编造的 CC 会话，AI 最后一句在问你，同时替身 loop 写一条「需要你决定」，等过核实时长
    预期：发件记录里只有 loop 那一张卡，没有 CC 会话的卡，也没有为 CC 会话发起的模型调用
A2. [乙-底座与托管] 操作：替身写「暂停：磁盘不足」，给的日志里其实是一条测试失败，等过核实时长
    预期：卡片写明「loop 说是磁盘不足，核实是测试失败」
A3. [乙-底座与托管] 操作：在一张「需要你决定」卡上点「按建议」，替身回执「已读」
    预期：替身收到的话和建议原文一字不差；原卡更新为已送达
A4. [乙-底座与托管] 操作：发卡后重启 PA
    预期：账本里的事情、派工、卡片状态都还在，旧卡不重发
A5. [丙-执行与自检] 操作：测试仓库里放一个带假密钥的改动，在做完卡上点 [推到仓库]
    预期：测试远端没有这个分支，原卡写明「发现疑似密钥，没推」
A6. [丙-执行与自检] 操作：让主进程停止更新心跳，超过设定时长
    预期：本机收到一条「personal agent 停了」通知，来自独立心跳
A7. [丁-飞书与派活] 操作：替身写一条「做完」，在假飞书渠道先问「<这个批次名>怎样了」，再发「那就先别合」
    预期：第二句的回复指向这个批次，意图卡出新版本，做完卡上的 [合入] 暂停
A8. [丁-飞书与派活] 操作：发「给 <测试项目> 的 <某文件> 补测试，门禁过就算完」，在派工建议卡上点 [派]
    预期：替身 loop 收到开批次请求，带配方名和定义；账本里出现这件事的派工
A9. [戊-放权与记忆] 操作：把「暂停：环境类 → 继续」设为自动，替身先写一条同类暂停，再写一条含红线的「需要你决定」
    预期：第一条 PA 直接送「继续」，原卡写「已按建议处理」带 [撤回]；第二条照样发卡等确认
A10. [己-侧边栏与日程] 操作：在侧边栏点一件「等你」的事，选建议
    预期：替身收到的话和在飞书卡片上点「按建议」相同，飞书原卡同步更新
