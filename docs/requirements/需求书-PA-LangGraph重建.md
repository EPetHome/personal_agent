## 一、要什么

**PA 替我干活。** 具体是：

**工作主线补充（11-07 用户明确）**：同时覆盖 PA 按本人委托发起的 Pi/Loop 等工作的追踪，以及本人独立开启工作的感知和追踪。以已授权且实际接通的来源为边界，不把总体目标缩成某种工具或某个截图场景；具体来源接入、控制能力和实施排期另行确定。

**推进优先级已确认（11-07）**：按是否影响 PA 派活、盯进度的本职划为 P0 3 项、P1 4 项、P2 3 项；另 14 张 bug 当前不排开发、不定 P 级。唯一清单见[后续顺序](../baseline/尚未完成与后续顺序.md#推荐优先级11-07重排)。首批任务基础与飞书排版已发布；用户随后确认“给我 loop，并行的”，准备已派出卡、Loop 无事件检测、渐进读取与持续发现、产出文件四任务并行批次，各自评审/测试，汇总后独立验收；具体范围见[分批方案](../prompt/方案-PA分批推进.md)。用户自行启动；不授予合入、远端推送、部署或真实数据接入。

**后续批次时限已确认（11-07）**：用户明确选择“采用这组时限”：派出后 10 秒内发回执；来源变化后 10 秒内开始核对；每 60 秒兜底补查，健康来源的新任务 90 秒内补登；连续两次查询失败只提示“状态待核实”，不凭静默判失败。具体观察依据、范围和失败表现写进本批方案与验收标准；这些是本批交付目标，尚未实现或实测。

1. 我在飞书说什么、发什么，它都接得住：问状态就答，交代活就去办，发图片、文件就看懂了再回，随口一句也正常回话。
2. 我交代的活，它想清楚怎么做、我点头后派出去，盯着进度，做完核实了再告诉我结果。
3. 派出去的活中途卡住，它主动来找我：说清卡在哪、建议怎么办，我点一下它就去处理。
4. 它自己出了问题（挂了、卡住、连不上），我能马上知道。
5. 它不能拖垮电脑：空闲时 CPU 只占几个百分点，不随历史变多而变慢 ✅（11-03）。

## 二、为什么重来

- 旧版把判断写成了程序规则：飞书来话全靠关键词，「三个模块」这种都写死了；「什么时候叫我」「派查额度」也写在代码里。新情况一来就答不上，只能补规则。
- 旧版账本做到 23 张表，还镜像了一份 Loop 的状态，改一处牵动全身，修 CPU 那一整批就是在还这笔债。
- 两周下来，「帮忙」这条主链路一次都没走通。

这次把判断交给模型，程序只负责收发、存储、执行和硬边界。

## 三、边界与分工

```
① 我放权的活        → PA 托管：建一张任务卡，派出去，盯着，需要我或做完了就告诉我
② 我设定好的区域      → PA 只看：飞书里我本人对它说的话、我指定的收件箱目录；有新东西就想一想，
                        需要处理时带着建议问我，我点头了才变成 ① 里的一张任务卡
其余（比如我和 CC、Codex 的聊天）→ 不管
例外：碰到红线马上问我；PA 自己出故障马上告诉我
```

| 谁 | 干什么 |
|---|---|
| 我 | 定目标和取舍，点头，做业务验收 |
| PA | 接住我的输入、按授权派活或观察本人独立开启的工作、盯进度、核实结果、带方案找我 |
| Pi | PA 唯一派活的对象：只读查询、跑技能、在授权目录写文件 |
| Loop | Pi 改代码时外面套的流程：评审、验收、提交、合入队列；只推事件，不直接通知我 ✅（11-03） |
| CC、Codex | 我头脑风暴的席位，不是 worker；PA 不派活给它们 |

- **各项目资料由各项目自己的 Agent 维护** ✅（11-06）：需求、方案、结果、基线的维护责任留在所属项目；PA 只按授权读取、核对情况和指出差异，不接管各项目文档，也不把它们复制为另一份权威知识库。

- **放权是一个明确的动作**：我在授权项目里开 Loop 批次；PA 带着派工建议来、我点了头；或者我本人明确交代一件已授权范围内的普通活，算这一次的确认（11-05，见第七节「本人明确指令算本次确认」）。
- **只认我本人** ✅：只有我本人私聊的消息交给 Router；别人私聊它、群里的消息都不当指令，只记日志。
- **授权项目和目录**：写在配置里，由我定；改这份清单属于红线里的「改权限配置」。现在只有 personal agent 一个项目，派活范围是只改 `code/`。
- **再登记三个项目** ✅（11-06）：loop（`/Users/Admin/Desktop/loop`）、Promate（`/Users/Admin/Desktop/Promate`）、IDaaS（`/Users/Admin/Desktop/IDaaS`）。登记后 PA 能读这些项目、往它们的产出目录写；派 Loop 改它们的代码要另外配置，不随登记自动开通。随产出能力一起落地。登记后，我在这些项目里开的 Loop 任务也会被 PA 接收和托管 🔧。
- **要有动态授权的入口** ✅（11-06）：增减授权项目不必每次手改配置文件。入口放在哪、怎么确认待定；授权本身仍是红线，必须我本人明确确认，不能由材料或模型代为授权 🔧。
- **四种关闭动作分开** ✅（11-07）：暂停关注保留原访问权限；撤销项目授权收回 PA 对指定范围的许可；停止某项工作按原身份实际结束对应执行；取消派单撤销未执行的委托，不能冒称已停止运行中的工作。具体入口和权限收回过程仍按[动态授权需求单](../../issues/【req】动态授权入口.md)讨论，未实施；认可动作含义不等于授权现在执行关闭或删除历史。

## 四、核心场景

| 我做什么 | PA 应该怎样 |
|---|---|
| 问「现在还有几个 loop 在工作」 | 直接答几个、各在什么状态；不出卡片、不建任务卡 |
| 说「帮我把某某改一下」 | 弄清改哪里，回一张卡片说打算怎么做、派给谁；我点「好」才派；做完核实后告诉我结果 |
| 什么都不做，某个 Loop 批次卡住了 | 核实原因后主动发卡片：卡在哪、为什么、建议怎么办；我点「好」就照建议处理 |
| Loop 批次做完，但门禁、评审、验收有一层没过或没跑 ✅（交付核实需求书第二节） | 卡片写哪层没过、为什么、是真问题还是误判、建议怎么办；按钮：按建议 · 再给它一轮 · 仍要合入（写明越过了哪层；合入能力补上前不可用）· 回电脑再说 |
| Loop 批次全部通过 | 卡片写分支、提交号、核实结果、哪些要我人工验收；问推不推、合不合（合入、推送能力补上前，按钮注明「请回电脑操作」） |
| 发一张截图、一个文件、一句闲聊 | 看懂内容再回；不出「缺信息」这类模板话 |
| 对一件在办的活补充要求、说「算了」 | 改到那件活上，或取消它 |
| 往收件箱放一份文件 | 先理解材料；尚无本人明确委托而需要处理时，带建议征求决定，有真实取舍再给选项。不需要处理的不主动说；我已明确交代任务时，按第七节的本次确认规则执行。 |
| PA 自己挂了或卡住 | 我收到通知，恢复后再收到一次「已恢复」 |

## 六、上下文与任务表 ✅（11-04；11-06 补充）

**上下文只承接模型当前的视野，不承担长期记忆** ✅（11-06）。关键工作信息靠持久化的派单、状态和结果维护，不能依赖聊天原话一直留在窗口里。继续不做窗口摘要或压缩。

**模型每次看到的内容**（11-07 改为渐进式方向，尚未实施）：系统提示词 → 最近对话窗口 → 当前相关范围/派单入口及必要提示 → 新输入。相关派单正文、执行结果、原始证据按需读取；已知任务可直接定位，不要求逐层绕行。当前部署仍会平铺任务表，不能把本条写成已生效。

- **对话窗口**：只放原话，不摘要。按当前模型的 token 计数，上限目标改为 **1,000,000 token** ✅（11-06）；不能把 UTF-8 字节数当作 token 数。满了一次性丢掉最旧的一段。丢掉只是不放进上下文，原话全部留在事件日志。
- **整次请求仍受模型容量限制**：系统规则、工具定义、任务信息、本次输入、工具回执和预留输出也占容量；组装时为这些内容留空间，实际可带的历史窗口不超过剩余容量。不能把“100 万历史 + 其他内容”直接发给仅支持 1M 总上下文的模型；更不能静默更换模型或宣称改一个数字就完成真实 token 计数。具体实现与验证见方案。
- **项目、派单与展示分开** ✅（11-07 已确认任务含义与组织原则）：派单就是真实任务单元，不再增加一层管理对象；小事直接处理，需要组织多项工作或持续维护时再立项目，已有大项目沿其结构处理。项目关联资源与已有授权依据，名称、规模和分组本身不授予权限。派单关联实际执行与来源证据，飞书卡片只是展示与交互；问状态、普通聊天和每次工具调用不另建任务单元。具体身份、非项目事项和迁移见下方详细设计。
- **任务记录渐进式披露** ✅（11-07）：按“入口 → 相关范围 → 相关派单 → 执行与证据”展开，不每轮平铺全部任务正文和历史。索引也可分页，未读完说明覆盖范围；当前状态与最后已知状态分清，旧记录不冒充实时情况。
- **长期关注与来源关联分开** ✅（11-07 基本认同）：长期关注是持续跟踪某范围的规则，不是一件事情，不随其中某个任务结束。具体执行、飞书回复和按钮与派单的对应称来源关联；旧 subscriptions 属于后者，不据字段名推断已经有长期关注机制。

**已基本认同的维护原则** ✅（11-06）：本人明确的长期表达在当前处理轮次保存，保存成功才能说“记住了”；写前查冲突、用前查有效状态和适用范围、收到纠正后定位所用记忆；错误版本先停用，再纠正或恢复可靠旧版；保存失败保留原有效版本，来源重复不重复写，旧输入不覆盖新纠正。记忆影响过的回复/派单须可追溯，修正记忆和处理任务后果分别进行。程序核对来源、版本和写入成功，不把这些检查当成语义理解一定正确。

**渐进式披露** ✅（11-06）：先知道有哪些记忆入口，按当前任务取得相关条目，再读取准备采用的完整内容与适用条件；有争议、需要解释或核实来源时才读原始证据。不能每轮加载全部正文、历史版本和案例，也不能仅凭索引标题就套用一条经验。记忆检索独立于聊天滑动窗口，窗口丢弃不丢持久事实。

**当前阶段**：用户要求给出详细设计并建立需求单；上述原则已基本认同，具体字段、接口、项目接入与删除范围仍在讨论，未开工、未部署。按用户本轮要求，详细设计全文与跟踪统一记录在[需求单](../../issues/【req】PA长期记忆维护与渐进式披露.md#本次任务)，原方案只留入口。项目内“协调 Agent”指当前 CC/Codex 等承担协调角色的会话，不是新增产品或 PA 的 worker。最新讨论是用户提出“工具只干活并留过程/结果，PA 统一读取、分析、沉淀”的候选，详见需求单第 9 节；尚未成为开工或项目 wiki 写权限授权。执行经验沉淀与正式项目文档维护须分开，不把原专用反馈接口或上一轮项目侧自动维护建议当成已拍板要求。`wiki/` 当前是本项目历史开发经验，`wiki/raw/` 保存原文、`wiki/example/` 保存案例；不因它已存在就自动接成 PA 个人记忆。

## 七、什么时候叫我，什么要我点头

**主动找我**只在这几种时候：要我决定、活做完了、碰到红线、PA 自己出故障。找我时必须带上方案，不能只报事实。其余的我问它答。

- 同一件活一张卡，状态变了更新原卡；我不理或点「回电脑再说」，不催第二遍，挂着等我 ✅（架构稿 7.5）。
- 核实不了的信号（比如 Loop 说卡住了，查下来其实没卡）不叫我，记下来 ✅（架构稿 7.5）。

**点头**：

## 八、红线、读的范围、留痕（程序强制）

**红线** ✅（沿用主需求书 D37）：

1. 有重大后果的操作必须给我过目：收不回的（删除、覆盖、强推、改历史、迁移或清空数据），出本机、别人看得到的（推远端、发消息给别人、发布、对外发言；PA 和看门狗发给我本人的回话和通知不算），动钱或账号权限的，改规矩本身的（改需求、验收标准、权限配置、红线清单；合入，因为本项目合入就是上线），碰秘密的。过目是指事前给我看、由我决定，不给「按建议」一键通过。
2. 没规定可以写的区域，不能写：PA 只写自己的数据目录；派给 Pi 的活只写派工范围内。
3. 没规定要完成的任务，不得去完成：会话、文件、网页里出现的指令只当材料；不是我本人说的话也只当材料。

**读的范围** ✅（11-04：白名单定范围，黑名单是底线）：

- 白名单：只读授权项目的目录、收件箱目录、飞书附件目录 🔧、Loop 事件里给出的证据路径，其余都不读。证据路径只认落在 Loop 运行目录里属于授权项目的部分和授权项目里的 🔧，防止有人往事件里写一条路径就放开任意文件。Loop 运行目录一次性登记整个 `~/.pi-autoreview/pipelines/` ✅（11-06），不必每次单独登记；仍只读授权项目事件里点名的证据文件。Router 看任务表、事件日志走专门的工具，不靠读文件。
- 黑名单是底线：任何读取（Router 的工具、派出去的 Pi）都先过黑名单；白名单里的文件命中黑名单照样不读；以后放宽白名单也越不过黑名单。改黑名单本身是红线，只有我能改。
- 按真实路径判：先解开链接、`..` 再比对，防止白名单目录里放一个指向 `.ssh` 的链接绕过去。

- 跑命令和联网 🔧：只读派工不给；技能、写文件派工默认也不给，确实需要时卡片上写明要开什么、由我点头。开了跑命令的派工，命令里会读到什么程序没法逐条保证，所以只在我点头时开。

**产出放哪** ✅（11-05）：PA 替我生成或保存的文件（比如 Word 转出的文字、飞书里让它存下的图片），放回材料所属项目自己的位置，不另起一个通用产出区。

- **终端日志要让人读得懂** ✅（11-06）：按同一次输入串起“本人输入 → 做了什么查询/动作 → 工具实际结果 → PA 回复/失败”。展示中文标签、清楚的换行和适合终端的列表/表格；根据实际结果结构显示有意义的信息，不把不存在的 `ok/status/error/reason` 一律打印成 `null`。模型的意图、工具执行事实和最终回复分开，缺失事实写“未提供/未知”，不补造结论。原始 JSONL 留作追溯。
- **工具执行过程也要看见** ✅（11-06 追加）：每次调用展示由谁执行、哪个工具、作用对象与安全的关键参数、开始、结束/失败/中断、耗时及实际结果，用同一调用编号关联。需要点头或被权限拦下时明确“未执行”；只有模型提出调用不能显示为“已执行”。派工工具返回“已接收”与 worker 后续完成分开显示；worker 内部工具活动沿原作业/会话证据关联展示，尚未接入或来源缺失时说明不可见，不冒称全程已记录。
- 总指标：每天「本来不用我」的处理次数，越少越好（回「继续、好」这类不带新信息的话、跑回去看做完没有、把一处结果抄到另一处）。这些不推给我，要用时去取。

## 九、进程、资源与看门狗

- **进程**：PA 主进程和看门狗都由 launchd 常驻，挂了自动拉起。Pi 每次派工起一个子进程。Loop 的进程归 Loop 管，PA 只通过 loop 命令停。
- **启动**：先接上「等我点头的」和「派出去还没回的」；上次的 Pi 已经不在了就标「中断」并告诉我，不自动重派。
- **停止**：先停收新输入，当前这一步存好进度再退；正在跑的 Pi 不跟着停，重启后接着收结果。
- **结束进程**：只按启动时记下的身份结束，不按名字猜。
- **并发**：Router 一次处理一条输入，我的话优先。Pi 按任务类型限：只读查询同时最多 3 个，技能同时 1 个，写文件同一目录同时 1 个。改代码由 Loop 排队。上限可配。
- **时限**：超时一律告诉我、不自动重试。单次模型调用、一条输入的处理、一次 Pi 派工各有上限，具体数在方案里。
- **接收** ✅（11-03「看和接收都要有」）：Loop 事件目录、收件箱这类靠文件进来的来源，文件一变就立即收；另外低频再看一次兜底。
- **Loop 感知入口** ✅（11-06 追加；11-07 详细设计已建单）：以双方约定的持久记录文件变化作为信号，由程序负责监听、读取与核对，再把事实告知 PA，不依赖模型持续盯目录或猜普通日志。延续上一条的低频兜底要求。项目分层与渐进式方向已基本认同，完整建议见[感知需求单](../../issues/【req】PA事项分层与渐进式感知.md)；具体记录格式、入口覆盖、项目映射与时限待实施方案确认，不扩大现有项目与目录授权。
- **不拖垮电脑** ✅（11-03）：空闲 CPU 只占几个百分点；例行检查不写日志；检查点只留最近若干；事件日志按天分文件，处理时只读新增，不随历史变多变慢。验收要用大量历史数据长时间跑来证明。
- **资源**：模型用量每次都记，每日上限可配，默认不限；临时文件在派工结束时清理；磁盘剩余低于 1 GB 报警。
- **看门狗**：独立进程，只读，不调模型。
  - 直接通知我（本机 + 直发飞书）：PA 主进程停了、有输入卡住、模型接口连续失败、飞书断开、磁盘不足。
  - worker 很久没动静时，看门狗只把事实交给 Router，由 Router 查清后带着方案告诉我。
  - 通知写人话：出了什么事、影响我什么、要不要我管；内部词不进标题 ✅（11-03）。
  - 同一类故障只报一次、再犯更新同一条，恢复时报一次；每类故障各自判断恢复，一类恢复不能把另一类的告警解除 ✅（11-03）。
