## 一、要点

- **定位**：PA 是给 Pi 和 loop 做的「Agent View」，加上飞书、微信、侧边栏和 IM 入口；替我完成被定义的工作。
- **边界**：只托管我放权的活和我设定好的区域；我的聊天不管；红线和 PA 自身故障例外。
- **分工**：CC、Codex 是我头脑风暴的席位，PA 不碰；Pi 是 PA 唯一派活的对象，改代码的外面套 loop。
- **流程**：两个入口汇进同一本账 → 派之前的检查 → 我点头 → 派工 → worker 回报 → PA 核实再叫我，卡片带方案 → 一批合成一次提交到批次分支，问我推不推、合不合；业务验收是我的事，不挡流程。
- **接口**：PA 只负责 router 到 worker 的接口；loop 要具备 7 项通讯能力。
- **不做**：盯我的聊天；判跑偏（暂时靠派单控制）；每日推送、周报、复盘。

## 二、为什么重画

两类问题，根子都在结构上，不在规则上。

**一是打扰。** 「叫与不叫」改了很多批：在场判断、等 5 分钟、合并提醒、按我在哪分三种、卡片格式改 5 批，结果仍有 98% 是无效提醒。协调方核对代码，原因如下：

| # | 根子 | 代码里的样子 | 后果 |
|---|---|---|---|
| 1 | 状态等于卡片 | `judge.ts` 的 `planNotices`：会话状态是在等我、疑似跑偏、停滞、loop 暂停或完成，就直接对应一种卡片 | 「值不值得叫我」没有一层专门判断，只能事后打补丁 |
| 2 | 单位是会话，不是事情 | 记录按「工具 + 项目 + 会话」组织，没有「事情」和意图卡 | 一件事跨几个会话就是几张卡；判断不了欠不欠我 |
| 3 | 把我正在聊的会话当成交出去的活来盯 | 用「最后一句话离 AI 停下不到 10 分钟」来近似区分 | 我正在聊的会话也会叫我 |
| 4 | 一个循环包办所有事 | `agent.ts` 的 `detect()` 每轮串行：全量扫文件、和 hook 推送对账、规则判断、发卡片、模型判断、再发卡片、维护 | 每轮 85～196 秒；改一处牵动全身 |
| 5 | 信号靠猜 | 「在等你」从会话文本、最后一句回复推断 | S-A 明确否决「从自由文本推断在等人」 |

**二是没减负。** 第二阶段起因（D34）：PA 只是流水线上的传递工，卡片陈述了事实，搬运还得我自己来。基线那一周（10-25 至 31）「粘贴材料」31 次、「同样开头的状态转述」18 次、「不带新信息的短回复」33 次。只会研判、不会搬运，减不了负。

## 三、PA 管什么

### 3.1 边界 ✅

```
① 我放权的活        → PA 托管：记一张单（派工），盯着，需要我或做完了就通知我
② 我设定好的区域      → PA 只看：有新东西进来就记下、想一想，带着选项问我要不要处理
   （飞书里对它说的话、     我点头了，才变成 ① 里的一张单
     我指定的目录、日历和会议）
其余（比如我的聊天）  → 不管
例外：碰到红线（推送、删除、合入）马上问我；PA 自己出故障马上告诉我
```

- **放权是一个明确的动作**：我启动 loop 批次；或者 PA 带着派工建议来、我点了头（在飞书、微信或侧边栏上）。动作发生时 PA 就记下这张单，不事后去猜哪个会话算交出去的。
- **我的聊天不管**：CC、Codex 停下不叫我，也不收成清单。叫我的意义是「我以为它在干活，其实它停了」，聊天时我本来就不指望它自己往前走。代价：我说完一句就走开、AI 马上停下问我，没人叫我，回来自己看。
- 主流也是这样（协调方 2026-11-02 查证）：[Claude Code 的 Agent View](https://code.claude.com/docs/en/agent-view) 用 `/bg` 把对话转到后台才开始管，只在需要你、完成、失败时通知；Codex 交出去时选 Ask（只读）或 Code（改代码）；[Cursor 接 Linear](https://linear.app/changelog/2025-08-21-cursor-agent) 是把 issue 指派给它；GitHub Agent HQ 在一个总控台派任务、看进度。Claude Code 自带的 Agent View 管不到 Pi 和 loop，也不上飞书，这就是 PA 的位置。

### 3.2 分工 ✅

| 谁 | 干什么 |
|---|---|
| CC、Codex | 我头脑风暴的席位：和我把任务定义清楚、干完核对结果。每件事谁当主力由我分配，另一个顶多做对抗评审，这一步我自己做。PA 不派活给它们、不往里送话（只有我在飞书说「转给 CC：……」时，把我的原话转进去） |
| Pi | PA 唯一派活的对象：查询（只读）、执行、跑固定流程（skills） |
| loop | 不是另一个执行器，是 Pi 干开发时外面套的流程：门禁、评审、验收、提交 |
| skills、LLM Wiki | Pi 执行时用的固定流程：摘要、沉淀进 wiki |

真机数据（10-15 至 11-01，只看会话记录的目录、来源和配置）：CC 153 个会话、Codex 158 个主会话，全开在项目根目录、陪我聊；Pi 374 个会话，在开发空间和 loop 的验收目录里干活。Codex 和 Pi 用同一个 OpenAI 订阅，差别在外壳：Pi 可编程，已经接进 loop 和 PA，所以只留 Pi 一条执行路径；Pi 出故障时，`bin/loop-dev codex` 可以临时顶上。

主流也按角色分，不按难易分：[Anthropic 多智能体调研系统](https://www.anthropic.com/engineering/multi-agent-research-system)主 agent 规划、子 agent 执行；Claude Code 的 opusplan 规划用 Opus、执行用 Sonnet；S-A、Sig 里选谁干活是程序规则。

### 3.3 定义 ✅

PA 替我完成的是**被定义的工作**，定义清楚了 AI 才能自动。「定义」指可核对：边界清楚、怎样算完成写得出来，也就是下面的意图卡 7 栏或 loop 批次的提示词。把事情定义出来也是 PA 的活：从我的话里起草，带选项来问我，不让定义的负担落回我身上。

**意图卡** ✅：决策之前的标准，不是决策的结果；是我的要求的可核对索引，不是第二份需求书，也不是 AI 给自己签发的通行证。只有我确认过的才算数，它起草、我没确认的内容不能放宽任何权限。

我看到的 7 栏（每栏都可以写「不知道 / 待确认 / 不适用」，不硬凑）：

1. 总目标：可以继承上一级的卡
2. 这次要的结果
3. 当前阶段：现在在哪一步，允许推进到哪一步、不允许什么
4. 不做什么
5. 操作边界：能读 / 能写 / 能执行 / 能动真机 / 能往外发，分开写
6. 怎样算完成：写明到哪一层（开发完成、门禁、评审、合入、真机、业务验收分开）
7. 要先问我的事：写成具体的触发条件，加上批的是哪个对象

- **放后台**：每条的依据（挂到来源那句话或任务文件那一行）、是否经我确认、版本和生效时间、替代了哪一版。实际进度另外存，不写回卡里。
- **谁写、什么时候写**：PA 从我的话里起草，我说了算；在第一个有副作用的动作之前要有可用的版本。有任务文件的（比如 loop 批次的提示词）直接对应过去，不另写一套。
- **什么时候让我确认**：按「要扩大什么权限」来确认：讨论转执行；新增读、写、执行、真机或往外发的范围；改目标、改不做什么、改完成标准；合入、发布、改权限。逐条确认，合在一起给我看。「按建议」只认紧跟的那一条；含糊的认同不算确认整张卡；沉默不算同意。
- **多大一件事算一张卡**：能独立判断结果、边界和完成的一件事算一张。同一目标下的澄清、返修更新原卡；从讨论到开发、从开发到发布各开一张子卡。卡和卡之间不能互借授权。
- **我中途改要求**：旧版本留着，记下来源那句话、改了哪栏、从什么时候生效、影响哪个待执行的动作；收紧的立刻暂停有冲突的动作，放宽的只放宽点名的那一项。做完的动作按当时那一版卡对照，不能用后来的授权追认；自动流程发的消息不能改标准或授权。

## 四、整体架构

```
┌─ 我
│ 头脑风暴：CC、Codex（PA 不管）
│ 放权：启动 loop 批次；或在卡片、飞书、微信、侧边栏上点头
└──────┬───────────────────────────────────────────▲──────────

       ▼                                            │
┌─ 感知 intake（程序）                          ┌─ 交互面 channel
│ loop 推来的事件                               │ 飞书卡片、企业微信、本机提醒
│ 飞书打字：问状态、回某张卡、转给 CC、交任务      │ 侧边栏：陈列 + 卡片上的动作 + 今天先做哪件
│ 指定目录的新文件                              └──────▲──────
│ 日历事件、会议纪要                                    │ 待发（已过围栏）

       ▼                                              │
┌─ 中枢：PA 常驻程序 + 账本 + 按需起的只读 Pi ─────────────┘
│ ledger 账本：事件 → 线索 → 事情（意图卡）⇄ 派工；唯一存状态的地方
│ assessor 研判（只读 Pi，想完就退）：核实、出方案、回答问话、派之前的检查、起草提问单和记忆候选
│ gate 闸门（程序）：只在需要我、做完、红线、PA 故障时打断；其余进陈列或等我问；开会时延后
│ 行动（都过围栏的档位：影子 → 建议 → 自动）
│   送话：我的原话送回 loop 的某一段；转给 CC：我的原话送进 CC 会话
│   执行：推批次分支、合入、停批次
│   派活：派之前的检查 → 我点头 → 派给 Pi（loop 批次、只读查询、skills）
│   代答：自动档下按建议送话，事后告诉我、能撤回
│   对话：我在飞书问，它从账本答
│   交接简报：批次卡死或被停时写
│ 记忆：规则参照、人、偏好、在忙什么（我确认才进）
└──────┬──────
       │ 待写（已过围栏）：先记、再送、确认；说不清就不重发
       ▼
┌─ worker-adapter（程序）：登记派工、收报告（先核实）、送话、执行
│ loop：7 项通讯能力　　Pi：PA 派出时自带登记
└──────┬──────
       ▼
┌─ worker（不重造）
│ Pi：查询（只读）、执行（改代码的外面套 loop）、skills、LLM Wiki
│ loop：配方（开发 / 只评审 / 只验收）
└──────

观测：核实结果、按建议的比例、loop 误报…… ──→ 观测记录 ──→ 记忆候选 ──（我确认）──→ 规则参照
watchdog（程序，只认机械事实）：派工停了、会话没了、来源看不见、话送不到、PA 故障；独立心跳
guard 围栏（横跨所有层）：红线、不许读、档位、留痕、撤回
```

### 4.1 层级与规矩 🔧

```
 第 0 层  外部        我 · 飞书 · 企业微信 · 指定目录 · 日历 · worker（Pi / loop）
 第 1 层  接入（程序）  intake（读进来） · channel（写给我） · worker-adapter（写给 worker）—— 只有这一层碰外部
 第 2 层  账本（程序）  事件 · 线索 · 事情 · 派工 · 待你决定 · 档位 · 记忆 · 待发 / 待写 —— 唯一存状态的地方
 第 3 层  决策          assessor（模型）· gate（程序）· 行动（程序）—— 不存状态，彼此不直接调用
 横切     guard：每条待发、待写，发出前都要过；watchdog：只读第 1、2 层的事实，只写回账本
```

1. 状态只存在账本里，其他部件都不存状态，重启从账本恢复。例外（2026-11-03 用户同意）：心跳、巡检时间这类运行信号写在单独的小状态文件里，覆盖写，不算业务状态；「上次查收件箱是什么时候」只记在内存，重启后马上查一次。
2. 只有接入层碰外部；assessor 可以只读原件和项目文件，受不许读名单约束。
3. 决策层之间通过账本通信：assessor 把结论写进账本，gate 再去读，「想」和「说」分开。
4. 对外只有两个口：channel（给我）、adapter（给 worker）；决策层只往账本写「待发」「待写」，发出前一律过围栏。
5. 依赖只能向下：加一个新来源只改接入层，换一个模型只改 assessor。

| 部件 | 读谁 | 写谁 | 不能碰 |
|---|---|---|---|
| intake | 外部来源 | 账本（事件） | worker、我 |
| assessor | 账本；只读的原件 | 账本（结论、候选） | 外部写入、channel |
| gate | 账本 | 账本（待发） | 外部 |
| 行动 | 账本、档位 | 账本（待写） | 外部 |
| guard | 待发、待写、意图卡、红线、档位 | 放行或拦下，留痕 | — |
| channel | 待发 | 我 | worker |
| worker-adapter | 待写；worker 的信号 | worker；账本（派工状态） | 我 |
| watchdog | 第 1、2 层的事实 | 账本（事实） | 外部 |

## 五、核心概念

| 概念 | 是什么 | 对应 S-A | 规则 |
|---|---|---|---|
| 事件 | 某时某处发生了一件事，写下就不改。比如「loop 批次 X 在 10:03 暂停」「我在飞书说了一句话」「收件箱里多了一份文档」 | Trigger | 状态都从事件推出来；事件本身不做判断 |
| 线索 | 一个来源里的一串东西：一个 loop 批次、一份材料、一段飞书对话 | Thread | 靠来源自带的身份归并（批次名、文件路径、对话），不靠模型猜 |
| 事情 | 我要的一件事 = 意图卡 + 关联的线索 + 状态 + 待你决定的问题 | Ticket + Mandate | 状态由事情自己定义；线索结束了，事情可以还没完；可以有上级事情，子卡继承总目标 |
| 待你决定 | 挂在事情上、需要我的一个具体问题，带选项和建议 | Attention | 除红线和 PA 故障外，唯一能打扰我的东西 |
| 派工 | 一件事交给 worker 做的一次绑定 | Assignment | 一件事可以前后有多次派工；派工结束不等于事情结束；写入只能指向一条明确的派工 |
| 档位 | 某一类动作现在是影子、建议还是自动 | 主动接活的三种模式 | 按「来源 × 动作」分别计（D15）；升级要我点头，降级快：自动处理被我撤回一次就退回建议 |

线索是「看」：凡是和这件事有关的都算，包括只拿来参考的材料；派工是「谁在做」，是送话、执行能写进去的唯一对象。S-A 也这样分：订阅只给上下文，派工才承担执行。

## 六、数据

按「跟着谁走」分四类：

```
┌─ A 账本：每件事的数据，随事情生灭
│   事情 ─┬─ 意图卡（有版本）     我要什么：7 栏
│         ├─ 状态                 从派工和事件推出
│         ├─ 待你决定（0～n 个）   具体问题，带选项和建议
│         ├─ 派工（1～n 次）       谁在做、做到哪
│         └─ 线索（1～n 条）       有关的批次、材料、对话
│   事情 ── 上级事情              子卡继承总目标
├─ B 全局记忆：跨事情、长期有效，只收我确认过的
│   规则参照：我的标准、同类问题我以前怎么定、wiki 里确认过的经验
│   人、偏好、我在忙什么
├─ C 围栏配置：只有我能改，改它本身就是红线
│   红线清单、不许读名单、每一类动作的档位
└─ D 观测记录：只增不改
    研判记录、送达和执行留痕、核实结果、按建议的比例、loop 误报、拦下的读取
```

| 数据 | 谁写 | 谁读 | 用来做什么 |
|---|---|---|---|
| 意图卡 | assessor 起草，我确认；loop 批次的提示词就是定义 | assessor、guard、行动 | 派之前够不够、动作在不在范围内、做完了没有 |
| 待你决定 | assessor 提出，gate 决定何时给我看 | gate、channel | 打扰我的唯一常规理由 |
| 派工 | worker-adapter | 账本、行动、watchdog | 写入的对象；谁在做 |
| 线索、事件 | intake | 账本、assessor | 事实依据 |
| 规则参照 | assessor 从观测里起草候选，我一键确认 | assessor | 建议的依据：同类问题我以前怎么定 |
| 人、偏好、在忙什么 | 同上 | assessor、gate | 排优先级、挑打扰的时机 |
| 红线、不许读、档位 | 只有我 | guard | 硬边界 |
| 观测记录 | 各部件追加 | 协调方、评测 | 放权的证据 |

意图卡回答「这件事我要什么」，事情结束就归档；规则参照回答「一贯以来我怎么定」，跨事情长期有效。意图卡不会自动变成规则，观测里的结论也不会自动写进任何长期数据，都要我确认。

### 7.2 账本和派工

| 派工字段 | 例子 | 用途 |
|---|---|---|
| 事情 | 「补登录模块的测试」 | 替哪件事干活 |
| worker | Pi / loop / 某个 skill | 决定用哪个 adapter |

- 一件事同一时间可以有多次派工；每次写入只能指向其中明确的一条，指不清就问我。

### 7.3 研判（assessor）

只读的 Pi，按需起、想完就退、不留会话；每次从账本拿相关的事实、原件和最近几句飞书对话，结论写回账本。它做这些事：

| 做什么 | 结论怎么用 |
|---|---|
| 核实 loop 的信号：是不是新的、真停了吗、原因对吗、真要我吗；「做完」的提交在不在 | 直接用 |
| 给卡片出方案，写依据（意图卡、提示词、规则参照、我说过的话）；没依据就写「没把握」 | 建议：我点了才算；够线的类别可以改自动 |
| 回答我在飞书的问话 | 直接用，只读账本 |
| 派之前的检查、起草提问单和派工建议 | 建议：我点了才派 |
| 起草规则、人物、偏好候选 | 我确认才进记忆 |
| 写交接简报 | 直接用 |

🔧 模型：日常用 DeepSeek v4.1 flash（经 opencode-go，不动 CC、Codex 的额度）；评测打分和抽样校准用更强的模型，不找我。拿不准就答「不确定」，转给我，不硬答。不判跑偏（第 7.10 节）。

### 7.5 卡片和按钮

```
worker 推来一个状态（信号）
   → 程序核实机械事实：是不是新的、过 3 分钟还停着吗（🔧）、「做完」的提交在不在
   → 研判读证据：原因对不对、真要我吗；出方案
   → 核实过、确实要我 → 一张卡：核实过的事实 + 方案 + 按钮
     核不实 → 不叫我，记成「loop 误报」，攒够了作为问题单提给 loop
```

| 卡片 | 带什么方案 | 按钮 |
|---|---|---|
| 需要你决定 | 建议选哪个，写依据 | [按建议] [其他选项] [我写一句] [回电脑再说] |
| 暂停（环境、方法、超时…） | 核实后的真实原因，建议怎么处理 | [按建议：发「继续……」] [停掉这批] [回电脑再说] |
| 返修到上限 | 剩下几条必修，每条建议怎么办 | [再给它一轮] [停掉这批] [回电脑再说] |
| 做完 | 分支、提交号、核实结果、哪几条要人工验收；建议推不推、合不合 | [推到仓库] [合入] [先放着] |

- **送话**类按钮（答复、继续、再给一轮）：我的原话送回 loop 的那一段。**执行**类按钮（推到仓库、合入、停掉这批）：PA 经 loop 去执行。都过围栏、留痕，按回执更新原卡；说不清就标「不确定」，不重发。
- 推送只推批次分支，不推 main、不强推，推之前查密钥；公开仓库在按钮上写明「公开」。合入用 [合入] 按钮，我点了才合（🔧）。
- 「按建议」只算确认紧跟的这一条（第 3.3 节）；红线类照样给建议，但按钮上写明我确认的是什么。
- 要 CC 处理的事，PA 不往 CC 里送，卡片提示我自己去说（🔧，CC、Codex 只属于我）。
- 我不理或点「回电脑再说」，不叫第二遍，挂在「等你」里。同一批次一张卡，状态变了更新原卡。

### 7.6 派活：一件事从进来到结束

```
 入口一：router（我不在场）              入口二：我在 CC、Codex 里定好，自己启动 loop
 飞书交任务、指定目录、会议纪要的待办              │
        │ 分拣 → 派之前的检查 → 缺事实就补         │
        │ → 派工建议 → 我点头                      │
        ▼                                         ▼
 ┌────────── 账本：事情 + 意图卡 + 派工 ──────────┐   ← 两个入口汇进同一本账
 └──────────────────────┬────────────────────────┘
                        ▼
              Pi 执行（改代码的外面套 loop）
                        │ 推事件：卡住 / 做完
                        ▼
      核实 → 卡片带方案 → 我点按钮 → 送话或执行
                        ▼
      做完：一批合成一次提交到批次分支 → 问我推不推、合不合 → 结束
```

**派之前的检查**：Pi 拿到手能不能直接开干，只看三样：

| 项 | 缺了怎么办 |
|---|---|
| 做什么：能不能定位到对象 | 先从我的原话和账本里找；找不到才补 |
| 怎样算完成 | 用项目默认，比如本项目：门禁过、评审无必修、提交到批次分支 |
| 能动什么 | 用项目规矩默认：只在开发空间、不合入、不推送、不碰真实账号 |

后两样永远有默认值；说「不够」必须指出缺哪一样；默认值只来自我确认过的规矩，写在派工建议上，我可以改。

**缺了怎么补**：

- 缺什么写清楚、列给我看，问要不要派一个只读的 Pi 去查；我过审才查，档位改成自动后不问。
- 只补事实（哪几个模块、测试在哪），不补取舍（覆盖率要多少、要不要顺手重构）；补上的每条事实写依据。取舍转给我，由我去 CC、Codex 头脑风暴。
- 不许无意义地烧额度：每次查询先填一张提问单（为了补哪一样、封闭问题和要交回什么、能看哪里、怎样算答完、预算），缺一样程序就不发；一次派、一次交，不来回对话；问到位就停，不追问第二轮；🔧 每件事最多 1 次、每天最多 5 次、每次 20 分钟。
- 补完以后还是同一件事：意图卡出新版本，查事实的派工结束，再开一个干活的派工。

```
事情：「补三个模块的测试」
  意图卡 v1：做什么？哪三个模块不知道 · 完成条件：默认 · 范围：默认
    ├─ 派工①：只读 Pi 查事实 ──交回──→ 意图卡 v2：做什么 = judge、agent、notify（依据：最近 3 次提交）
    │                                  取舍：覆盖率要到多少？→ 带选项问我 → 意图卡 v3：我确认
    └─ 派工②：Pi（套 loop）干活 ──做完──→ 提交到批次分支 → 问我推不推、合不合
```

**派给谁**：改代码的开 loop 批次（按意图卡选配方）；只要事实的派只读 Pi；摘要、沉淀进 wiki 这类固定流程，派 Pi 跑对应的 skill。

**终点**：一批合成一次提交，提交到批次分支，记下分支和提交号；做完卡问我推不推、合不合。合入就是上线，业务验收是我的事，都不挡流程。

### 7.7 放权和记忆

- **档位**：按「来源 × 动作」分别计，默认「建议」。某一类够了线（🔧 样本至少 20 条、和我一致至少 9/10、严重错误 0 次），卡片提示「这类可以改自动」，我点了才改。只有能撤回、或者错了我能及时发现的，才进自动。自动处理的，事后在原卡写明「已按建议处理」，带 [撤回]。收回：被我撤回一次或出一次严重错误，就退回上一档。红线永远不自动。派活同样可以改自动。每改一次模型、提示词或规则，都用评测集重测一遍。
- **规则参照**：assessor 从观测里找我对同类问题的一贯选法，起草规则候选，发一张卡让我一键确认；确认的才进，带版本，改了记下；出方案时引用。
- **人、偏好、在忙什么**：同样起草候选、我确认才进；用来排优先级、挑打扰的时机。

### 7.10 watchdog 和独立心跳

watchdog 只认机械事实，不做语义判断，自己不发消息；事实写进账本，由闸门决定打不打扰我。

| 盯什么 | 机械事实 | 交给闸门后 |
|---|---|---|
| 派工停了 | 在做，但超过一段时间没有任何事件 | 进陈列 |
| 会话没了 | 派工的会话消失，事情还没完 | 进陈列：这件事没人在做了 |
| 来源看不见 | loop、飞书等来源读不了 | 马上告诉我 |
| 话送不到 | 送话或执行失败 | 马上告诉我 |
| PA 自己 | 检测失败、磁盘满、渠道连续失败 | 马上告诉我 |

**独立心跳**：launchd 下另一个极小的定时任务，只看主进程的心跳多久没更新，太久就直接弹一条本机通知；不依赖主进程，也不依赖飞书。心跳记的是「主流程最近一次完成一轮的时间」（主流程堵住也算停）；2026-11-03 起心跳和巡检时间写在单独的小状态文件里，覆盖写，不往账本追加（见第 4.1 节规矩 1 的例外）。

**PA 自己的故障怎么报** ✅（2026-11-03）：同一类故障只有一张卡，再犯就更新这张卡；恢复后发一次「已恢复」。卡上写人话：出了什么事、影响我什么、要不要我管。

**PA 自身不能拖垮电脑** ✅（2026-11-03）：常驻时空闲 CPU 只占几个百分点；账本只记真正发生的事，例行检查（「查过了」「我还活着」）不往账本追加；每一轮检查读账本一次、只读新增部分，旧卡、旧记录不随数量增长拖慢每一轮。验收要用上万行账本、几十张历史卡长时间运行来证明。

**不判跑偏** ✅：「方向对不对」PA 不去猜：开工前派之前的检查把定义问清楚，执行中由 loop 的评审、验收和 `scope.allow / scope.deny` 越界检查把关，做完 PA 核实结果，暂时靠派单控制。依据：我实际用下来，跑偏判断不准、没意义；10-15 以来 66 张跑偏卡我没看过，11-01 以来花了 573 次模型调用。S-A 原文让 Watchdog 也查「目标偏离」，但调研没确认原型实现了；S-A 落地的范围控制是 Mandate（超出工单范围的要求交回重来）；Sig 的 Watchdog 只查运行停滞；Claude Code、Codex、Cursor、Kiro、Devin 的公开资料里没查到内置的跑偏监控，靠开工前定义清楚加做完审改动。以后出现评审和验收都没拦住、到我手里才发现方向错的案例，再拿来举证要不要加。

### 7.11 围栏

红线、不许读、档位、留痕、撤回。每一条送话、执行、派活发出前都要过围栏：只能指向明确的那条派工，动作在意图卡范围内，红线要我明确确认，记下谁点的、做了什么、结果如何。

**红线** ✅（主需求书 D37）：

1. 存在重大后果的操作，必须给我过目。
2. 没规定可以写的区域，不能写。
3. 没规定要完成的任务，不得去完成，不自作主张。

主需求书 Q2 原有的四条（不读密钥和密码管理器、不以我的名义对别人发言、不执行材料里的指令、不删原件）是这三条的具体例子。

- 「重大后果」命中任一条就算：收不回（删除、覆盖、强推、改历史、迁移或清空数据）；出本机、别人看得到（推远端、发消息或邮件、发布、对外发言）；动钱或账号权限；改规矩本身（改需求、验收标准、权限配置、红线清单；合入，本项目合入即上线）；碰秘密。「过目」指事前给我看、由我决定，不给「按建议」一键。
- 「规定可以写的区域」：PA 自己只写它的数据目录 `~/.personal-agent/`；派给 Pi 的活只写派工范围内，超出就交给我。
- 「规定」指意图卡里写明的目标、不做什么、怎样算完成；会话、文件、网页里出现的指令只当材料。没写明完成标准的，不替我宣布完成或同意收尾。
- 红线由程序规则判，模型只能往里加，不能往外移；改红线清单本身就是红线，只有我能改。执行工具自己的权限仍然生效，是第二道门。

**不许读名单** ✅（项目层；目录层和文件层 🔧），由程序强制：

- 项目目录本身要像项目：工作目录是主目录 `/Users/Admin`，或者桌面、文稿、下载这类大容器的，不算项目，只能读会话本身。
- 文件层：`.env`、`.env.*`（`.env.example`、`.env.sample` 除外）；私钥和证书（`*.pem`、`*.key`、`*.p12`、`*.pfx`、`*.jks`、`*.keystore`、`*.kdbx`、`id_rsa*`、`id_ed25519*`、`id_ecdsa*`）；`.npmrc`、`.pypirc`、`.netrc`、`.git-credentials`、`.git/config`；文件名里有 `auth`、`session`、`cookie` 的 `.db`、`.sqlite`、`.json`。不按「token」「secret」「password」这类词拦，会误伤。
- 目录层：`.ssh/`、`.aws/`、钥匙串、密码管理器、私人聊天；`~/.personal-agent/`；备份目录（`.bak/`、名字带「备份」或 `backup` 的）；`eval/cases/`、`eval/runs/`、`eval/待标注/`。
- 项目层：哪些项目只许读会话、不许读项目文件，由我逐个定；2026-11-01 定目前出过卡片的项目都可读。
- 读到的内容会作为输入发给模型服务（DeepSeek，经 opencode-go 中转），不只留在本机。

**必须满足** ✅：每次替我做的事都留痕，能查到依据；拿不准就问我；只有能撤回或错了我能及时发现的才进自动；命中红线永远交给我；收集数据不让我额外投入（主需求书 D38），反馈、标注由 AI 从我本来就会做的事里推断，我不操作不当信号。它替我做了什么、哪些和我不一致，放进陈列，我问它答，不推送。

### 7.12 节奏：事件驱动

事件到了（loop 推事件、我在飞书打字、新文件、日历变化）才处理相关的那件事，不再每轮扫全部。

**看和接收都要有** ✅（2026-11-03）：Loop 事件目录、收件箱这类靠文件进来的来源，文件一变就靠系统的文件变化通知立即接收；另外低频再看一次兜底，防止通知漏掉。收到后只处理相关的那件事。低频巡检兜底（🔧 10 分钟），只查过了时间才成立的事：核实的 3 分钟、派工停了、会话没了。

### 7.13 观测：准不准怎么量

旧设计靠我在卡片上点「正确 / 误报」，我几乎不点（D38），所以准确率一直量不出来。新设计把大部分「猜」换成「核实」，正确答案从事后的事实和我本来就要做的选择里自动拿：

| 判断 | 正确答案从哪来 | 量什么 |
|---|---|---|
| 核实 loop 的信号 | loop 后来是否自己恢复、日志、我点了什么 | 叫错率、漏叫率 |
| 「做完」是真的吗 | 分支上的提交、各项结论 | 程序直接对 |
| 卡片上的方案 | 我反正要选 | 按建议的比例 |
| 派之前的检查 | 派出去后有没有被问回来「到底做什么」、我有没有改定义 | 被问回来的比例 |
| 回答问话 | 账本里的事实；我回「不对」 | 对不上的次数 |

**总指标** ✅：每天「本来不用我」的处理次数，越少越好。只数那些不需要我、却非得我来做的处理：回「继续、好、可以」这类不带新信息的话，点不涉及红线的「允许」，跑回去看做完没有，把一处的结果抄到另一处。我给新信息、定方向、做取舍、改要求、拍板红线的，都不算。新 PA 里按「核实后没叫我」「自动档替我处理了」「我按了建议」来数。基线（10-25 至 31）：不带新信息的短回复每天约 5 次、卡片每天约 70 张；粘贴材料 31 次、同样开头的状态转述 18 次，可能是人工搬运。

**每次模型分析都要记下**：看了哪些材料（路径、行号、内容指纹）、用的模型和提示词版本、它的判断和理由、给的方案、最后实际发生了什么（自动做了 / 我按建议做了 / 我改了 / 我没理）。

另外记 loop 误报、查询花费。这些都不推给我，协调方要用时去取；评测集判定点按上表改写。

## 九、设计尺子

借用 S-A 的第一原则：**用尽量少的我的注意力，换尽量多的价值。**

- 举证倒置：上线以后，每种卡片、每个设置、每个功能都要证明「给的价值 > 花掉的注意力或复杂度」，证明不了就删；决定放不放权也看证据。它不用来拖延开发：定下的设计一次建成（✅ 2026-11-02）。
- 多一层就多一个维护点：没有需求证明，不加层。
- 概念要少：新需求先变成已有概念的一个属性，不新增概念。
- 嫌吵就删：不用新消息去解释噪音。
