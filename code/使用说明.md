本版已有真实 Loop/Pi 接入实现和临时资源验证，**不表示开发方已经部署真机或接通真实账号**。当前 Loop 的推送/合入预期目标绑定、推送秘密扫描和只验收配方有接口缺口，明确不开放；见下节。

当前运行入口消费 **loop JSONL 事件**，以及显式启用的收件箱、飞书日历和妙记；不再解析 loop 总结出卡；不扫描 CC/Codex/单独 Pi 聊天、不消费聊天 hook、不判跑偏、不生成日报/周报/复盘。`src/core/agent.ts` 和 `sources/loop/index.ts` 只留作历史兼容/离线回放，不被当前 CLI 检测和常驻调用。

新状态唯一来源是显式 `dataDir/ledger.jsonl`。旧数据不迁移、不清理、不补发旧卡，不重写旧 `state.json`。loop 送话、补查与派工默认**建议档**，可按来源×动作分别设为影子或经本人确认改自动；推送、合入、停止及所有红线仍逐条明确确认，都经 worker-adapter 交给 loop。自动处理在原卡交代，带撤回自动授权；已经送出/执行的动作不冒充可收回。规则、人物、偏好和在忙什么均先出候选卡，确认后才进全局记忆。交接简报、机械 watchdog、独立心跳和飞书文字问答/明确转 CC 沿用。

- 只评审须额外配置 `loop.review:{"base":"明确提交或分支","head":"明确提交或分支"}`，映射为官方 `review-only`，无产品写权、不返修、不进合入队列。`acceptance_only` 当前明确拒绝，不降级成开发。


预检不写配置、数据、plist、Loop状态或备份；列拟改文件和缺项，不读 `.env`。应用保留凭据**引用**、所有旧字段/输入前缀/数据；只更换显式连接配置并补 Loop `pa.eventsDir`，保留 `localNotify` 等原设置，不自动关通知。已有入口只核对不重写；同名他人入口拒绝覆盖。新入口仅生成文件，**不自动 bootstrap**；新安装仍须获准操作者核对后按原 launchd 方法加载。不要对已经生成的同名 plist 再执行拒绝覆盖的 `service-install`。

`--reload` 仅对已加载的明确入口，先 `launchctl print` 核对活动 plist 路径，再 `kickstart -k` 原 label；不按名称猜进程、不接管独立侧边栏。省略时不启动/重载任何服务；由协调方按原启动方式恢复。重复应用相同配置返回 `unchanged`，不重载或覆盖；部分应用/重载未知时保留 `$BACKUP/manifest.json` 和现场，不盲目重试。此快照仅含配置/入口，**不是数据备份**。

应用后再对新配置运行 `probe.ts`：它只运行官方 `查询 --all --json`、Pi `--version`、已配置 whisper `--help` 和 ffmpeg `-version`，核对本地模型文件存在，不调用模型、不登录、不刷新 token。确认模型目录/凭据时可由获准操作者用 Pi 的 `--offline --no-extensions --no-context-files --no-skills --no-mcp --list-models <型号>` 和 `pi auth check --model <型号> --json --no-refresh`；**不得加 `--credentials`，不得用 print-api-key/print-bearer-token**。探测可运行不等于模型质量或业务通过。

回退入口：

```bash
node code/deploy/connect.ts --rollback "$BACKUP"
# 仅在原两项已加载且确需恢复运行时，显式加 --launchctl /bin/launchctl
```

回退只还原本次配置/入口原字节，不碰原数据/材料，也不撤销已经执行的业务；部署后被别人改过的文件拒绝自动覆盖。先停写者；新生成入口若后来被人工加载，先按原方法卸载它再回退。代码退回由协调方对未来本批合入提交执行 `git revert`；不能填一个尚未存在的提交号。需回到旧版数据时用下文升级前完整副本，不拼账本。

### 3. 真实协议与尚未就绪项

真实 Loop 以实施时本机源码为准（本次核对 `8977976`，不是永久版本常量），见其 [工具清单 PA 对接](../../loop/工具清单.md#pa-对接)。PA 保留官方 v1 原事件 `native`、UUID/seq、批次文件、配方、原始证据对象与来源文件；内部仅将 `done/needs-decision/repair-limit` 转为原账本状态，将 `stage:null` 标成 `@batch`。同项目同名不同文件不混成一件。生命周期与队列分别登记，同轮 `done → queue` 不抹掉完成卡、门禁/评审和人工欠项；队列前两次退回只陈列，第三次仍回原卡并保留原完成依据，队列未就绪不借旧完成卡放行发布。整批层没有会话字段表示不适用，不当作会话已消失；实际段明确不存活仍进卡住/等你。送话核对项目+文件+名称，未唯一定位不执行。查询只用 **查询**，不调用会恢复队列的 **状态**。

段暂停走 `送话 <file> --stage <stage> --id <id> --text-file - --wait 0 --json`，stdin空白/换行不改；`delivered` 只表示已投递，`read` 才是已读。官方 `resumed{via:pa,id}` 或只读查询 `paRelays` 可核销已读，不靠重发查回执。整批 `resume` 走 `续跑`，只接受明确“继续/恢复/再给一轮”，不静默丢掉任意原话；`grant` 原文走 `--grant-file -`，自动档不能代答授权；`manual` 不给续跑按钮。续跑 `started` 仅表示编排启动，不表示段已读、验收或业务通过。未知请求一律不重投。

当前 Loop `parseArgs/pushQueueBatch` 没有接收本人确认的 expected 分支/提交，推送也没有所需的完整秘密扫描。PA不能用一次预检封闭后续竞态，因此真实 worker **拒绝推送/合入，完成卡不提供这两个可执行按钮**；停止走官方登记归属核对入口。未修改 Loop、不手动 Git 合并、不改完成资格放行。这是本批未补齐项，不以已有队列CAS冒充用户目标绑定。

Pi `protocol:pi-v1` 直接使用配置的真实 Pi CLI，不再把裸Pi塞给旧JSON替身协议：程序强制 `--no-tools --no-session --no-extensions --no-context-files --no-skills --no-prompt-templates --no-mcp --no-themes --no-approve --offline --mode json -p`，固定系统指令，预读范围受 `ReadSandbox` 和提问单双重约束。材料模型没有写工具/自由shell；任何工具调用型回执不当成功。`summary/wiki/transcribe` 是按本人skill名称映射的固定处理器，**不是自动发现/执行任意 SKILL.md 脚本**。摘要/wiki由禁工具Pi交回纯正文，程序独占创建 `workspace/pa-results/<requestId>/summary.md|wiki.md`；转写只调用明确配置的本地whisper与已有模型，读本次私有原件快照。产物路径由程序决定，拒绝模型自带路径，已有目录不覆盖；原件前后哈希/身份重核，`sources.json` 可核对来源。不自动写进权威 wiki 或提升成长期记忆。摘要/wiki 的输入限可安全预读的文本或转写文本；图片/PDF 内容解析未实现，不能把缺读取能力报为已处理。

### 4. 日历/妙记授权准备（由用户授权，未就绪不冒充接通）

应用凭据不是用户token。缺 `FEISHU_USER_ACCESS_TOKEN` 时来源健康明确写“日历/妙记未就绪：缺少本人用户授权”；预检/能力探测不会读取秘密或替用户授权。准备时先列当前实现要用的只读API：日历实例视图、妙记基础信息、AI产物/文字导出；只有配置 `minuteOwnerIds` 才需要妙记搜索。对应精确scope由飞书官方API页/应用后台当前权限表核对，不猜授予整账号或消息写权限。

依据协调方已核对的[授权码文档](https://open.feishu.cn/document/authentication-management/access-token/obtain-oauth-code)和[v3 token 文档](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3)：

1. 用户在自己的应用后台核对并发布最小只读权限，登记受控 `redirect_uri`。授权端点为 `https://accounts.feishu.cn/open-apis/authen/v1/authorize`；参数含 `client_id/redirect_uri/scope/state`，PKCE 使用本次随机 verifier 对应的 S256 challenge。state/回调不匹配立即终止，不接受材料给的回调/链接。
2. 用户本人打开授权页核对账号、资源范围与scope后决定。授权码只交给受控本地兑换端，不粘到聊天、JSON配置、账本或日志。用官方 v3 `https://accounts.feishu.cn/oauth/v3/token` 按当前文档兑换，**不再使用已弃用的 v2 user_access_token 接口**。本文不提供假兑换器，也未执行真实兑换。
3. access token 仅写入数据目录外、0600、已忽略的外部 `.env` 的 `FEISHU_USER_ACCESS_TOKEN`，保留原 `FEISHU_APP_ID/FEISHU_APP_SECRET` 引用。不要打印文件或 token。若文件位于任何Git仓库内，先只核对 `git check-ignore`；未忽略不得保存/提交。授权码、verifier、refresh token也不能写进账本/产物/提交。
4. 只有用户另行明确同意 `offline_access` 才可保存 refresh token并走官方v3受控刷新；本版运行端**不自动刷新**。未同意不申请，过期要明确报来源未就绪/权限故障，不能拿应用tenant token顶替。长期授权闭环仍需获准外部凭据管理方式，不把静态token读取说成长期授权已解决。
5. 将本人选定日历/妙记/所有者ID填入 `schedule`，`mode:real`，`envFile` 指向该外部 `.env`。空资源白名单不访问。先由用户看范围再启用真实资源，不用假渠道冒充已接账号。

- 候选提交只在 `worker.candidateRefs` 白名单的 ref 上核实；loop 不能把任意分支自称为合入候选。真实 loop 的候选 ref 不同，由获准操作者明确映射配置。
- `judge` 用既有只读 Pi：禁工具、会话、扩展、上下文文件、skills、模板和自动更新，输入由读取沙箱提供的受控证据。进程想完即退出。`--offline` 不禁止显式模型请求，自动测试必须指向替身。
- `judge.dailyLimit` 缺省不限，0 禁调用，正整数为 UTC 每日上限。`timeoutMs` 限单次，`cycleTimeoutMs` 限一次处理的模型总时间（默认60秒）；耗尽后规则兜底，不挡收件。调用失败同样计入已保存研判。未配模型、额度不足、超时/坏答案时使用**写明没把握**的规则方案，不偷偷启动真实模型。
- 核实默认 3 分钟，从 PA 实际收到本次停下信号计时；同一连续停止不被重复事件重置。巡检默认 10 分钟。loop接入与每个渠道的收件分别独立调度，默认间隔500ms，只唤醒有变化的事件链，不再整轮扫描/调用模型。模型或飞书文字确认很慢/超时时，新loop事件仍先入账并唤醒处理。
- `staleAfterMs` 默认 30 分钟，仅把“长时间没有新事件”放进等你清单，不推、不据总结年龄猜停工。只读状态给出有效 `lastActivityAt` 时可核销停滞；查询时刻本身不是活动证据。
- 旧 `service.intervalMs` 不再驱动大循环；`restartWindowMs/restartThreshold` 继续保留异常重启告警。旧 `waiting/intelligence/learning` 开关仍忽略，不恢复被删行为。
- 没有 feishu/localChannel/judge 时主进程不连接飞书、不弹本机、不调用模型。独立心跳是另一个显式安装/运行的入口，通知命令缺省 `/usr/bin/osascript`；**测试须设置 `heartbeat.executable` 为通知替身**。假飞书不替换 worker/CC/心跳通知，离线验证务必显式配置对应替身。

## 替身与事件

`code/test/loop-stub.ts` 的所有数据都放在第一个显式参数指定的临时目录。`emit` 接完整事件并追加到临时收件目录：

```bash
node code/test/loop-stub.ts "$WORKER_DIR" emit "$INBOX_DIR" < "$EVENT_JSON"
```

`EVENT_JSON` 的例子（路径换成构造项目，文件名与 batch 一致）：

```json
{"schema":1,"id":"synthetic-decision-1","seq":2,"at":"2026-11-02T10:00:00Z","project":"/tmp/pa-demo/project","batch":"构造批次","stage":"乙","state":"needs_decision","reason":{"category":"decision","text":"需要你决定"},"evidence":["/tmp/pa-demo/project/gate.log"],"detail":{"question":"旧测试要顺手改吗？","options":["改","不改"]}}
```

状态：`started / needs_decision / paused / repair_limit / completed / failed / resumed / queue`，字段按方案附件。producer **只追加完整 JSON 行并带换行**；不覆盖同 inode 的已消费前缀。PA 按事件 `id` 去重，按段保留最新 `seq`，迟到事件保留原件但不倒退状态。未写完的半行等待续写，非法整行留指纹并隔离；单文件失效不拖垮其他批次。

- `started`：立即登记事情、线索、意图 v1 和具体段的派工，不发卡。意图保存七栏、来源、版本和可继承的上级总目标；继承不复制授权。原 loop 提示词仍是任务定义，不由模型另造执行权限。
- `needs_decision/paused/repair_limit/failed`：先记待核实，3 分钟内同段恢复则不叫；到期再只读查状态和证据。
- `completed`：立即只读验证报告的 commit 是否位于报告的批次分支或配置候选；只在对象库有对象不算证明。候选上可证时写“还没提交到分支”，不可证时写“说做完了，没找到提交”。门禁、评审、验收是 loop 报告，卡片明确标来源，人工项/失败/部分验证分别保留。
- `queue`：前两次 `returned` 仅进等你；第 3 次推卡。巡检只读补回漏掉的状态变化，补回后仍过同一个等待/核实链路，不触发 loop 恢复、重测。

替身设置：

```bash
printf '%s\n' '{"receipt":"uncertain"}' | node code/test/loop-stub.ts "$WORKER_DIR" set
# receipt 可为 delivered / consumed / uncertain / failed；dropReceipt:true 模拟已收却丢回执。
# status 可填方案附件2的完整响应，模拟恢复或漏掉事件；statusError:true 模拟查询失败。
```

查看替身目录：`events.jsonl` 为已发事件，`queries.jsonl` 为只读查询，`attempts.jsonl` 为每次送话/执行调用，`received.jsonl` 为收到的话/执行请求，`executions.jsonl` 为执行请求，`starts.jsonl` 为收到的开批次请求，`receipts.jsonl` 为回执。替身推送能真正推到**同一临时根内的本机裸仓库**；合入、停止只模拟 loop 回执，不实际合入工程或停止别的进程；不开真实批次。

替身执行须在 `settings.json` 中显式设置 `allowExecution:true`、`projects:["/临时根/测试项目"]` 和 `pushTarget:{"remote":"test","visibility":"public"}`（或 `private/unknown`）。这是替身造的公开状态，不连接托管平台。远端须只有一个推送URL且为同一临时根内的绝对裸仓库路径；网络和当前产品仓库均不允许。三卡演示已创建这些条件及通知替身。设置 `omitExecutionResult:true` 可模拟收到请求却没有结果/提交号，PA 只能标不确定。

Pi 替身的 `--model` 指向构造 JSON：

```json
{"answer":{"suggestion":"不改，记问题单另开批","basis":"依据原问题与任务范围，不顺手扩大范围","redline":false},"capture":"/tmp/pa-demo/model-calls.jsonl"}
```

可加 `fail:true` / `delayMs` 验证失败或慢研判；`usage:{"input":7,"output":3,"totalTokens":10,"cost":{"total":0.00001}}` 可构造用量元数据。不读取真实模型凭证。

- `schedule` 缺省关闭；日历/妙记ID数组为空时对应来源不读。`minuteTokens` 是妙记**资源标识符，不是访问凭证**。可选 `minuteOwnerIds` 只读搜索这些明确所有者近7天的新妙记（一次最多1000项，超限报故障不当成功）；不默认搜索全账号。SDK按50项分页；假渠道按相同所有者白名单选取构造条目。未选所有者/资源不进账本。

### 真实授权边界与恢复

本批自动验证不接真实账号。合入后由用户将 `schedule.mode` 改为real、配置明确日历/妙记/所有者，按官方上述只读API申请权限并授权；`fakeFile`在real模式不用。SDK需要用户身份的 `FEISHU_USER_ACCESS_TOKEN`，与 `FEISHU_APP_ID / FEISHU_APP_SECRET` 一样只放进程环境或数据目录外、已忽略的 `.env`（可用 `schedule.envFile`，否则沿用 `feishu.envFile`）；不要把凭证填进JSON、材料或账本。应用tenant token不能代替用户token。用户token到期/权限不足会报来源故障，需用户更新授权，本批不自动登录或扩大账号权限。真实飞书手机是否对原卡更新发通知、真实OAuth/模型/worker/skills能力不由替身验证替代。

上线前仍须停全部写者、完整备份数据目录、配置和启动入口，再换代码；没有真实迁移、没有删除旧文件。恢复使用下文的独立完整副本，包含新账本和假渠道原件；收件箱外部原件保持原路径/身份，变化不能靠修改指纹放行。退回不认识新表的旧版须用升级前完整备份，不能拿新版WAL直接给旧版读。

## 检测、时钟、查询与常驻

```bash
node code/src/cli/main.ts detect --config "$CONFIG" --now '2026-11-02T10:00:00Z' --json
node code/src/cli/main.ts detect --config "$CONFIG" --now '2026-11-02T10:03:00Z' --json
node code/src/cli/main.ts overview --config "$CONFIG" --json
node code/src/cli/main.ts rebuild --config "$CONFIG" --json
node code/src/cli/main.ts stats --config "$CONFIG" --json
node code/src/cli/main.ts daemon --config "$CONFIG"
```

`overview/rebuild/stats` 只重放账本，不读来源、不起模型、不投递、不另存状态缓存。JSON 中 `tickets / assignments / assessments / attentions / cards / writes / deliveries / handoffs / proposals / conversations / observations` 可核对全链路。事情 `status` 与 worker 的 `reportedState` 分开：`running` 在跑、`pending_verification` 待核实、`waiting_user` 等你、`needs_verification` 完成报告待核对、`done_pending_actions` 已交回待后续动作、`waiting` 只陈列；`merged/stopped` 来自本人明确确认的执行回执。worker 报 completed 不等于事情结束、合入或业务通过。`stats` 只显示观测计数，不主动推送。

单轮可用带时区的 `--now` 快进并固定整次离线回放时间；不带 `--now` 的CLI和常驻在每次渠道投递前使用当前时钟判会议，不沿用轮次开始时间。常驻可在构造测试中注入 `runService(config, signal, {now})`，单轮核心入口也可传 `processManagedLoop(config, at, {channels, now})`。研判或前一渠道跨过会议开始/结束时，后一投递重新判断；若sending落盘后、实际调用渠道前才跨入会议，恢复为pending等待，不算已调用或渠道故障，会后仍按原请求防重。亦可在**测试配置**中把 `verifyAfterMs/inspectEveryMs/intakeEveryMs` 调短；上线默认值不变。daemon 不接受 `--now`，Ctrl-C/SIGTERM 正常退出。收件与研判分别调度，10 分钟巡检不是常规事件的等待条件。

## 假飞书、按钮与回执

`feishu.mode: fake` 不加载真实连接、不读 `.env`，出卡/更新/文字确认的副本在 `$DATA/feishu-sent.jsonl`。该文件是渠道审计副本，**不负责恢复当前状态**；消息映射、待发、回执和连接状态以账本为准。已有发送记录也作为禁止重复回话的只读证据，不因新账本回执缺口重发。

第一次 managed 启动/接入/发卡先在账本保存新旧收件边界：此前已存在的整个收件前缀都不重放，不根据旧回执是否齐全猜测年代。旧成功/失败/仅ID人工核销回执、旧回复发送证据也只用于排除历史重投，不搬成新处理状态，不补发旧确认。边界之后的新点击仍可操作旧卡。用假渠道从零演示或沿用旧目录时，先启动一次 daemon 或执行一次 `feishu-poll` 建立边界，再追加新点击；三卡演示脚本已建立边界。边界保存历史原字节前缀的SHA-256及字节数/行数，启动和收件处理前都校验：完整副本的inode可以不同，前缀内容或边界改变/截断则停止处理并保留现场，不重设边界放行。

向 `$DATA/feishu-inbox.jsonl` 追加一行（`noticeId`、`revision` 与 `messageId` 从最新原卡/账本取）：

```json
{"id":"synthetic-click-1","at":"2026-11-02T10:03:01Z","actor":"ou_test","type":"action","messageId":"om_fake_从原卡取","value":{"action":"managed_suggest","noticeId":"loop-从原卡取","revision":"1"}}
```

```bash
node code/src/cli/main.ts feishu-poll --config "$CONFIG" --now '2026-11-02T10:03:01Z'
```

动作：`managed_suggest` 按建议；`managed_option` 加 `option:"0"` 等原选项下标；`managed_manual` 打开“我写一句”；表单 `managed_send_text` 加 `relayText` 原话；`managed_continue / managed_repair` 送“继续 / 再给一轮”；`managed_defer` 进等你不催；`managed_withdraw` 对人工请求只撤回尚未投递的待写；对自动请求还会收回这一类的自动授权、退回建议档，不能收回已执行的外部动作。执行用 `managed_push / managed_merge / managed_stop`，不能用 `managed_suggest` 代替。

- 只接受配置的本人；回调核对原卡消息、版本、事件、意图版本和**具体派工**。缺段、不匹配、过期、收紧后的请求不送，不猜最近批次。旧JSON送话接口缺少可靠文件身份时仍拦下同名多项目歧义；真实接口另绑定project/batchFile/name/stage，不靠最近会话猜目标。
- 按建议只送紧跟的一条，字节空白/换行保留，不附带“同意整张卡”或隐藏指令。
- 红线由程序硬判，模型只能加不能减。红线卡没有“按建议”一键，按钮写明要转达的原话；原选项不隐藏，分别用明确确认选项按钮（`managed_confirm` 加 option 下标）。红线卡上的手写回复先固定全文、更新原卡，再要求 `managed_confirm` 明确确认。
- 先保存待写和操作者/依据，再 `sending` 落盘，再调用一次 worker。`delivered/consumed` 更新原卡为已送达/已读；`uncertain` 或进程在发送后没记回执，都标不确定，不重发。相同请求号、同次决定重复点击都不会二次投。
- 原卡的送达、已读、输入框、恢复只更新，不再次弹本机。新的需要决定/暂停/返修上限/完成事实才打断；同批次始终更新原卡。
- 新渠道确定拒收最多 5 次，停发后仅尝试一次本机告知；重启核对同卡同渠道**所有版本**的遗留 sending，转为不确定。无法确认旧首发且无 messageId 时，即使恢复/完成使卡片换版本，也不新建第二张卡；已知 messageId 的后续变化只更新原卡。外部 API 与本地 WAL 无原子事务，不承诺严格 exactly-once。
- 旧卡 CC 原话转达与旧反馈的显式兼容入口保留，转达总开关仍默认关；不会常驻扫描聊天。新文字入口见下节。
- “正确 / 误报 / 漏了 / 看不懂”在新链路只入账观测，不生成汇总/记忆。未知引用不退回最近一张；本机 `feedback` 仍可显式指定旧卡编号走旧兼容。

真实渠道只有获准后才接入，凭证只能在进程环境或数据目录外的已忽略 `.env`。自动检查不接真实账号；真实手机、卡片更新是否会产生平台通知、真实权限与网络体验仍需联调/人工核验。

## 飞书打字与派活（丁）

只接受 `receiverId` 本人在 p2p 的文字；原反馈词优先，继续只记观测。不必起模型才能问状态或交一个明确任务。最近12句原话和明确指向的事情存 `conversations`，重启不丢；未知引用、重名批次、无上下文的「别合」不猜目标。

- 「现在有什么等我」「<批次名>怎样了」只从账本答，附账本身份/版本/时点，不冒充worker实时状态。
- 引用需要决定卡说「选 B」等同“我写一句”，逐字送回原段；涉及红线的原话仍先出明确确认，不直接发送。
- 「那就先别合」「不要推送」「暂停派工」使原事情意图出新版本，保存来源整句、变动字段、受影响的待写；旧确认失效，相关按钮/待写暂停。后续「允许合入」只恢复合入按钮，仍须本人再点明确按钮，不连带恢复推送/派工。每个授权词组只绑定一个动作或明确并列的动作组，后置「可以」不能再次借给下一动作：「合入可以而推送不可以」只恢复合入，和「允许合入，不允许推送」一致。引文只作材料；否定优先，疑问、条件或无法可靠归属的肯定不解除限制。目标、完成条件或范围变更先冻结旧派工/发布许可，不把新要求追认给已完成动作。
- 只在整句以「转给 CC：」或「转给CC:」开头时转达。冒号后的空格、换行、原文不改；仅此时读取显式CC目录，按普通会话文件最近修改时间固定一个目标，不因它忙而悄悄选旧会话。发送仍复用 `cc-relay` 的总开关、在跑登记唯一且idle、完整回合结束、游标未变、会话锁、stdin原话、原会话核实和不确定不重发；红线原话须卡片再确认。回执原卡写明会话号与cwd。其他「让CC处理」只提示本人去说，不转达。显式CC转达的正文即使是「给 src/widget.ts 补测试」，仍只是原话搬运，不套PA派工的开发配方选择；总开关、目标/原话绑定、idle核实、红线确认与不确定不重发照旧。

三卡演示 `managed-demo.ts` 已配置下列构造项目、Pi替身、`modules.md` 清单、假 `recording.wav`；沿用演示输出的 `config.json` 即可。生产配置需由本人指定项目和开发空间；项目和skill写根须存在，Loop的新开发空间可由官方开工创建；路径须为真实路径（在macOS用 `realpath` 后的 `/private/tmp/...`，不是链接/别名）。未配置的项目不猜写范围。

`done` 省略时采用示例中的项目规矩；原话写「门禁过就算完」则卡片明确用这条完成条件。范围默认只读配置项目、只写配置开发空间；只评审/只验收/只要事实不准改产品文件。只读/普通任务/Pi skill均不碰真实账号、不合入、不推送；用户点派只批准展示的定义和范围，不给泛化执行权限。

- 明确只评审/只验收的阶段限制先于修改词：只评审（含「不改代码」）→loop `review_only`，只验收（含「不修复代码」）→`acceptance_only`，写范围必须为空。实际代码修改→`develop`，附带总结不降级为裸Pi skill；不得从否定或材料中的修改指令获得写权。
- 反引号/引号中的纯文件路径是对象，不是一段指令：如“修改 `src/widget.ts`，并总结结果”保留文件类型、走开发loop；整段引用的“修改代码并补测试”仍只作材料。原话/路径原件不改，授权判断视图也不会从文件名推断允许合入等动作。
- 正向任务与局部禁改分开：转写摘要“不修改原文件”仍派对应Pi skills，补测试“不修改配置文件”仍开开发loop。禁改原句写入 `definition.nonGoals` 和可选的 `definition.boundaries.prohibitedChanges`，卡片单列“禁改”；同一边界完整传给loop定义及Pi的 `constraints.scope`。派出前guard拒绝丢失/放宽这些边界的可写请求，真实执行端必须落实禁改对象，不能把这份请求当成权限沙箱的替代。
- 只要事实→Pi `query`；转写/摘要/wiki→Pi `skill` + 配置映射的固定skill名，skills也只从正向任务选取；引用或禁改中的词不新增skill。完整原话继续保留，材料不能提供命令或新授权。
- 缺省/`protocol:json` 的 `piWorker` 是**受信任的JSON命令接入端**，不能把普通 `pi` 二进制直接填进这个旧协议。真实Pi请显式用页首 `protocol:pi-v1`。PA执行 `<executable> <args> query|skill`，stdin一次请求、stdout一次JSON回执，无shell拼接。真实Pi/skill接入端须落实只读/写范围、原件不覆盖、不对外发送、禁合入/推送等第二道权限；当前自动验证用随仓替身，不偷偷起真实Pi。未配置或接口不符明确失败，不冒充执行。

### 补查、回执和预算

提问单 `sheet` 必须齐全：`goal`、封闭 `questions`、`boundary`（read/write/tools/outbound/realDevice）、`arrival`、`budget:{timeoutMs:1200000,maxRounds:1}`。缺一项程序拦下。每件事最多一次、当地自然日最多5次，点查时在同一账本事务预留名额，旧按钮/并发点击不能超额；已派出但失败/未知也计一次，未发的撤回不计。第六次只列缺项；隔天重置日上限，不重置每事情一次。

PA通过原有 `ReadSandbox` 预读本项目索引（100项）和最多20个原件（每份150行/8KiB），附同项目账本上下文。Pi收到 `constraints:{readOnly:true,tools:[],noSession:true,maxRounds:1}` 与“不可信材料”标识，不开放自由shell/写工具。读审计只记范围/指纹、不记正文。单次命令及准备/依据核对合计预算不超过20分钟；测试可以把 `piWorker.timeoutMs` 调短，原预算不放宽。

Pi回执：

```json
{"requestId":"原请求号","status":"consumed","facts":[{"text":"alpha、beta、gamma三个构造模块","basis":"/实际构造项目/modules.md:1"}],"questions":["还要你定的取舍？"]}
```

事实依据须可定位为允许读取的 `绝对路径:行号`、本次 `index:<项目路径>` 或 `账本:<事情id>`；秘密/不存在的依据不当事实。PA不保证模型事实语义一定正确，卡片明说是Pi交回、附依据供核对。交回后同一意图出新版本、查询派工结束、原卡写事实与最多3个问题；不做第二轮自动追查。用户接「那就按这三个补测试」在**同一事情**出新的干活建议，查询依据作为独立材料随派工带上，再点[派]才开loop。已结束的Pi补查（成功或失败）只保留历史，不压住后续干活的在跑/完成状态；loop提交按Git研判核实，Pi结果按单次派工回执判断，不要求Pi查询有Git提交。

`pi-worker-stub.ts` 的 `settings.json` 可设 `facts/questions/result/status/delayMs/waitFor/dropReceipt/rawReceipt`；查看 `received.jsonl` 的 `action/query|skill`、提问单、配方或skills，以及 `receipts.jsonl`。默认事实依据指向演示 `modules.md:1`。skill只模拟交回，不真实转写录音。可用 `rawReceipt` 造坏回执；`dropReceipt:true` 造已收却丢回执。loop/Pi均按requestId记录，不再发第二次；PA崩溃后的sending也标不确定。

loop `start`请求含 `schema/requestId/proposalId/ticketId/project/batch/kind/recipe/definition/source/mode`，定义为点头的七栏意图、精确版本和边界；有事实材料时带 `contextFacts`，有关联简报时带最新 `handoff` 五栏，不复制全部历史。新批次后续事件按已登记的project/batch接回同一事情/原卡；送话仍单独点头。账本派工的 `startRequestId` 绑定原启动待写；启动回执未知不结束这条绑定、不重派。即使首事件未送到，也参加只读巡检，按状态报告的实际段补回事件（停下仍先等核实时间），Pi查询/skill不参加loop巡检。多段报告接在原事情；合成事件不冒充worker真实seq，尚未知时派工seq为-1，后来的真实seq=0可正常接入。可信首事件或状态事实在 `receipts["start-evidence:<requestId>"]` 留依据，把未知启动核销为已确认，保留用户原意图和暂停要求。早期缺startRequestId或已误置endedAt的未知启动记录，从同一派工的原待写核对绑定；只追加事实，不重写/迁移旧文件。

常驻的Pi长查询/skill独立消费账本待写，不占loop核实/发卡与主心跳；退出会取消Pi子进程并保存未知回执。迟到结果只入原派工，不覆盖新版意图、新卡或worker新事件。一次性CLI则等本次执行器交回后退出。

## 放权和记忆（戊）

### 档位与提示线

- `modes` 在同一本账本里。`shadow` 只记录、不推普通卡、不送话/派活；`suggest` 默认，逐条点；`auto` 仅在本人明确确认该类之后处理。红线在任何档位都照常出明确确认卡，不会被影子隐藏或自动执行。
- loop 送话按 `loop × reply:<事件类型>:<原因类别>` 分开，例如 `loop:reply:paused:environment`；派工按来源×执行器/配方/skills/项目/读写及禁改范围的指纹分开，不跨项目、配方或范围借权。档位卡展示具体项目与边界，不让用户只凭指纹放权。CC 转达不进入自动派活。
- `choices` 只计成功送达/已读的本人选择；同一事情同一事件只计一次。失败、被拦、重复回调、自动结果不算正向样本。每代至少20条、与本人一致至少九成、严重错误0次，才出现一张「这类可以改自动」卡；提示本身不改档。点 `managed_mode_auto`（明确确认这一类设为自动）才生效，伪造普通“按建议”不能改权限。
- 原卡的 `managed_mode_settings` 打开这一类的档位卡；该卡可用 `managed_mode_shadow / managed_mode_suggest` 明确切到影子/建议。每次改档记录操作者、真实输入、前后档位及版本；旧改档按钮失效。退档后须重新攒人工样本，不立刻重复提示；严重错误不会因换代清零。
- 只有定义/边界完整、非红线、能在原卡及时发现结果的动作可自动。送话仍须机械核实该段确实停着；飞书须已连接（fake-poll会登记fake可用），而且实际卡片发送/更新不能处于未核实恢复的故障中。准入和发出前都检查：`connected`或文字回话成功不能证明卡片可达。
- 当前卡片渠道状态单独记在 `health["card-channel:feishu"]`；实际失败、超时和崩溃后未决发送会暂停依赖飞书原卡的自动动作，只有故障已入账后开始的实际卡片成功可恢复。`deliveries.attemptSeq`、故障事务号及恢复投递号留在账本，旧在途成功不能核销新故障。旧账本只有deliveries失败、没有这份检查点时也先暂停，新的成功才能证明恢复；不重写旧失败记录。
- 正常卡片仍在`sending`时，尚未尝试的自动派工/补查只等待回执：保留pending、派工建议和预算预留，不移除按钮、不先调worker。回执成功后由独立派工循环重新核对当前意图、档位、范围和预算，合格才派一次；等待中改档收回授权仍会取消未发请求。实际失败/uncertain仍拦下，遗留sending仍由渠道恢复核销为uncertain；已尝试的worker请求不会进入这个等待分支或被重试。历史blocked不因新逻辑自动复活。
- 通道恢复不等于某张未决卡已送达：失败/未确认的原卡还需同卡、不早于失败版本的成功送达。未知首发无messageId时仍不重建第二张；其他卡恢复成功只允许其他已具备条件的卡继续自动。`health["write:…"]`只表示某次历史worker请求失败，保留告警和原回执，不把它当成永久的全局飞书故障；该类的严重错误/退档记录也不会被通道恢复清除。
- 补查的完整定义是只读提问单，不是尚缺事实的原开发任务：原任务的missing不妨碍合格补查计样本。提问单必须有目标、封闭问题、允许读取范围、到位标准、最多20分钟/1轮预算；读取范围与意图一致，没有产品写权、真机或对外发送权限。20次成功人工查询可提示改自动；已交回的查询只作为资格证据，不再次派出。每事情最多1次、每日最多5次仍在行动及真正派出前检查，补查结果不能自动授权后续开发。其他开发/skill派工仍须对象与定义完整。
- 派出前重新核对精确派工、当前意图、档位版本、本人改档输入、实际卡片可达性及全部原有围栏/补查预算；模型不能给自己改档。
- 自动送话不再弹本机，原卡写「已按建议处理」与实际回执；自动派工事后原卡写「已自动派」，二者都有[撤回]。自动请求的操作者是 `pa:auto`，另绑定本人改档的输入号，不伪造一次本人点击。adapter送话用 `source:pa_auto`，派工另用 `mode:auto`；人工仍是 `source:user_via_pa, mode:suggest`。真实接入端须识别这一区别，执行红线绝不因auto字段放宽。
- [撤回]取消同类尚未发出的自动请求，并退回建议；已经送出或已执行的动作**不能由现有loop协议收回**，原卡明确提示核对结果，不发相反指令来假装撤销。要停止已派出的批次仍须本人点明确的[停掉这批]红线按钮。撤回/旧回执不重发、不重复降档。
- 原卡可报 `managed_feedback_严重错误`，或引用卡片发「严重错误 + 说明」：一次就退回上一档（自动→建议、建议→影子），并留下严重错误记录；重复反馈不多降。自动请求失败或结果未知也保守退回建议、不重发；失败与业务严重错误均不自动清零。

### 记忆候选与问答

- 同类「需要你决定」的问题（项目、原因类别、原问题与选项均相同）连续5次本人选同一项，就起草规则候选。只有 `managed_memory_confirm`（确认这一条记忆）才写 `memories`，带确认人、输入、来源、版本；`managed_memory_dismiss`只略过。规则候选和观测不会自动变成权限或记忆。
- 下一次同类建议可引用已确认规则，明确写 `规则参照 memory:… vN`；未确认的候选完全不注入研判。规则只作参照，仍需按当前意图、红线和档位核对。不同问题/选项不套用；模型只能起草人物/偏好/忙碌候选，不能把自写的规则当作用户的一贯选择。
- 飞书本人可写「张三：Promate 的产品负责人」「我偏好先处理短任务」「我最近在忙秋季发布」来起草候选；也支持明确格式「人物：张三：Promate 的产品负责人」「偏好：沟通：先给结论」「在忙什么：本周：秋季发布」。只读研判的可选 `memoryCandidates` 也只进候选，单次最多3条，不直接进记忆。
- 点人物候选确认后问「张三相关的事」，从账本列直接提到张三或其已确认关联词（例如Promate）的事，附账本依据；未确认不从候选或最近聊天推断人物关系。直接问「我的偏好」「我在忙什么」「规则参照」也只列已确认版本；研判只拿已确认记忆作参照。
- 同一人物/偏好/忙碌主题的新陈述会起草下一版本，仍需确认，旧确认版本保留。候选绑定其预期旧版本；另一张候选先确认后，过期候选不能覆盖新版本。改记忆不追认旧动作、不改变意图卡、档位或红线。
- 新增状态均在 `ledger.jsonl`：`modes / choices / memoryCandidates / memories`，没有另一份长期记忆文件。旧观测、意图卡、旧learning库不迁移为新记忆。备份/恢复仍按文末整目录副本方法；旧版代码不认识新增表时不能直接读新版账本。

## 执行、交接简报与 watchdog

- 做完卡的 [推到仓库]、[合入] 绑定只读核实的批次分支和完整提交；不可证或 `main/master` 不提供执行。只在候选上可证时可合入但不能推分支：卡片、批准、待写和请求都绑定核实得到的candidateRef与完整提交，执行端核对该候选ref的精确头，不要求尚未更新/不存在的批次分支包含它；不能从分支不符时自动猜其他候选。缺远端信息不猜着推。卡住的卡提供 [停掉这批]。
- 公开远端按钮写 [推到仓库（公开）]；未知写“可见性未知，可能公开”。点击只生成这条派工/动作/提交的意图版本和待写，不授予泛化或自动权限。发出前再过围栏、再核对目标/可见性；先保存 sending，再调用 adapter。
- 密钥扫描由 **loop 执行端**负责，不让 PA 越过 read-sandbox 读密钥，也不让 PA 自己跑 git push/merge。替身扫描待推历史的逐提交补丁（包括后来删去的密钥）、暂存/工作区/未跟踪改动；疑似内容/敏感文件名或扫描不完整均拒推，只回安全原因，不回原文。这不保证识别所有秘密。
- 成功按 `pushed/merged/stopped` 更新原卡为已推送/已合入/已停，带回执提交号；推送号须等于确认的号。合入/停止关闭这批派工和等待项。只有 delivered/consumed 而没有执行结果，不能冒充成功；超时、丢回执、崩溃 sending 均不确定、不重发。停批次没回提交时不编造。
- 返修上限经核实后、停止成功时，存 `handoffs` 五栏：`goal / progress / decisions / unresolved / codeLocation`（目标、做到哪、关键决定、遗留问题、代码位置）。`overview --json` 可按 ticketId 查；纯文本 overview 也显示。丁段开新批可取同事情最新一份。
- watchdog 不起模型、不碰外部、不自己发消息。成功 status 的 `sessionPresent:false` 或对应段消失、事情还未完成时，只记“这件事没人在做了”进等你；恢复/完成/停止后核销。超过 staleAfterMs 没事件也只陈列，不猜跑偏；查询失败不是会话消失。
- 来源目录、worker 只读查询、飞书连接/收件失败，送话/执行失败或适配器错误、PA 处理故障，均记机械事实给闸门发故障卡；送话失败当次立即发“话没送到”，不等巡检。磁盘满等不能记账的情况保留既有本机紧急兜底。

### worker-adapter 旧JSON协议（替身/兼容；不等于当前Loop官方能力）

`status` 在原字段上增加 `pushTarget:{remote:"test",visibility:"public|private|unknown"}`；每段可加 `sessionId` 和布尔 `sessionPresent`。候选身份可由原有 `candidateRef` 或 `queue.candidateRef` 给出；没给名字时仍只核实显式配置白名单里的ref，不接受任意来源扩权。执行追加英文 `push / merge / stop`，stdin 示例：

```json
{"requestId":"pa-…","project":"/临时根/测试项目","batch":"构造批次","stage":"丙","action":"push","branch":"feat/demo","commit":"完整hash","remote":"test","visibility":"public","source":"user_via_pa","force":false,"checkSecrets":true,"protectedBranches":["main","master"]}
```

merge 不带远端；候选合入另带 `candidateRef:"refs/pa/candidate"`（实际为核实过的白名单ref），普通批次分支合入不带此字段。stop 不带分支/提交。PA在发出候选合入前复查当前 `worker.candidateRefs`，执行端也用自己的获准候选白名单独立检查，不能靠请求扩大白名单；替身用 `settings.candidateRefs`，缺省同为 `refs/pa/candidate`、`refs/loop/candidate`，自定义时两端分别显式配置。候选被删除、头已移动、status换了身份均拦下，不偷偷改指向；缺身份的旧待写不补授权。loop 必须按 requestId 幂等，在执行瞬间核对项目/批次、批准的分支或候选ref精确头、远端与可见性；推送必须完成扫描、只推精确批次分支、不强推。回执沿用 status，另给 `outcome:pushed|merged|stopped|blocked`；成功推送/合入给完整 commit。疑似密钥回 `status:failed,outcome:blocked,code:suspected_secret`，不回原文。真实 loop 未满足这些前提不得用于真实执行；当前只验证替身链路。

## 独立心跳与 launchd

主进程默认每30秒在账本记录进展，正常空闲也更新；处理失败不会用独立计时器掩盖主循环停摆。独立任务默认每60秒看心跳，超过180秒就弹本机“personal agent 停了”，不依赖主进程、飞书、worker。测试可调短上述三项，everyMs 须小于 timeoutMs。先留尝试再通知，结果不明不重弹；恢复后再次停摆可报新一条。从未启动不报警。

两个任务分别显式安装；下面仅生成到**临时目录**，不激活、不触碰真实 LaunchAgents：

```bash
node code/src/cli/main.ts service-install --config "$CONFIG" --target "$TEMP_AGENTS"
node code/src/cli/main.ts heartbeat-install --config "$CONFIG" --target "$TEMP_AGENTS"
node code/src/cli/main.ts heartbeat-check --config "$CONFIG" --now '2026-11-02T10:10:00Z' --json
# 卸载先独立任务再主服务，以精确移除本次创建的空目录：
node code/src/cli/main.ts heartbeat-uninstall --config "$CONFIG" --target "$TEMP_AGENTS"
node code/src/cli/main.ts service-uninstall --config "$CONFIG" --target "$TEMP_AGENTS"
```

独立 plist 为 `local.personal-agent.heartbeat.plist`，StartInterval 向上取整秒且至少1秒，固定 argv 调 heartbeat-check；主 plist 仍调 daemon。真实安装须另获准，`--activate` 才调用 launchctl；测试激活只能用 `--launchctl` 替身。均保留冲突拒绝覆盖、摘要、归属核对、不误停同名服务保护。

心跳与通知去重也在 ledger.jsonl，没有第二份权威状态。独立任务可恢复死进程留下的已知短锁；未知/活锁、坏账本不自动删或截断；并发检查忙时不重复通知。账本损坏或无法写入时，独立任务降级为本机“心跳无法核实”，不另造权威状态、不输出原始异常；因无法持久化去重，后续调度可能再次提示直到修复。完整备份包含账本与渠道原件；恢复后先核对是否仍应常驻，再安装独立任务。

## 围栏、证据与账本

PA中枢仅写显式数据目录；获准adapter另按本次配置创建批次定义/产物，部署入口只改显式配置/入口并留独立快照。产品代码工作由官方Loop处理，不裸跑Pi。测试/演示只写新的临时目录；PA只派本人逐条确认或明确授权该类自动的本次定义，不越过adapter扩大范围。

- 每条待写发送前重新核对意图版本/本人点击或该类自动授权/精确派工；红线单独确认。留痕含谁点的、原话、依据、目标、结果；撤回不是把已经送出的话“收回”。
- 原件通过 `read-sandbox` 的 read 工具授权；Git 机械核实同样先授权项目根，不能借 Git 绕读秘密目录。`.env`、秘密目录、其他聊天、链接、硬链接等继续拦截。显式 loop 证据例外不绕过不许读名单。
- 会话/文件/网页里的指令只是材料，不能授予权限或指定执行命令。模型只能写建议和依据，不能改问题原文、机械核实结果、按钮目标或档位。
- 账本一事务一行、顺序链与 SHA-256 校验、fsync 后才有副作用；短锁不含模型、worker、渠道调用。重放恢复事情/派工/待决定/待发/待写/回执/卡片版本/档位/读审计与观测。
- 观测只追加：已确认叫了几次、核实后没叫几次、按建议比例、loop 误报、查询次数与耗时。Pi 回报用量时另记 token 与 USD 估算；没回报就列 unknown 次数，不冒充零花费，也不把 Pi 报价当实际账单。被新事件取代的研判仍保留花费。渠道失败只留受控类别，不复制原始上游异常。

## 数据、备份与恢复（上线前必须做）

**没有迁移旧库。开发没有读取、备份或改动真实 `~/.personal-agent/`，也没有部署。** 新结构从获准上线后开始记。完整备份/切换由获准操作者执行：

1. 停止旧 PA 和所有旧写者，保留配置及 launchd 入口；不要同时运行新旧版。
2. 完整复制显式数据目录到新的备份目录（例如 `cp -a "$DATA" "$NEW_BACKUP"`，目标必须尚不存在），同时保存配置与启动入口；不要只备份一个 JSONL。
3. 核对备份可读后才切换代码/启动配置。新版只新增 `ledger.jsonl` 并继续追加必要的渠道/服务审计，不删除/改写旧事实文件，不运行旧库归档/清理。
4. 新版自身恢复：停写者，保留损坏现场的完整副本，把同一备份时点的 `ledger.jsonl` 与相关收件/渠道审计按原字节恢复到一个**独立的新目录**，让配置指向它。`overview --json` 仅校验账本重放，不代表渠道已经可用；正常启动时、以及处理新按钮/反馈前，PA会核对账本保存的收件历史前缀SHA-256和字节/行数，允许完整副本的设备号/inode变化。内容不符、截断、坏账本/半行会报错停下，不自动重设边界、拼接或重发不确定请求。
5. 回退旧版：先保留新版完整现场，再由协调方回退本批未来的合入提交，让旧版使用**升级前整目录备份的独立副本**。旧版不理解新账本，不混拼新旧事件，不删除新账本凑兼容。本批尚未合入，不能填写已执行的 revert 提交号。
